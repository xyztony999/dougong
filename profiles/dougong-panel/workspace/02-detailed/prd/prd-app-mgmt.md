## 第一部分：业务目标（G1）

为登录运维者提供 **Python 应用的面板化托管能力**：用户在面板服务器上部署自有 Python 应用（如 nim-proxy——FastAPI + uvicorn + requirements.txt 形态）时，手工串「装运行时 → 建 venv → 装依赖 → 写 systemd 服务 → 建反代站点 → 看日志」六步成本高且易错。本模块（用户 2026-11-20 拍板）把这六步收拢为应用生命周期管理：**创建应用（目录校验 → venv → 依赖安装 → 生成 systemd 服务）→ 运行管理（启停/自启/参数/日志）→ 对外暴露（建站联动）→ 删除（保守保全）**。

**运行时供给与既有模块协同（Q2 拍板）**：Python 运行环境本体由 env-mgmt 供给（本轮第九环境增量 +python，发行版仓库包无第三方源代配，⚠️A18）；本模块经环境实况读契约消费依赖就绪度（python3/venv/pip 已装态与能力位），环境缺失时如实拒绝并软引导到环境管理（不代装）。

**部署路线拍板（Q1）**：venv + systemd 为主——与面板现有架构一致（env-mgmt 装环境、服务走 systemd、site-mgmt 建站反代）；容器路线不在本轮（容器管理能力已在 docker-mgmt——admin 有完整启停/删除/日志/Compose 编排能力，「只读」现象经链路核验为 readonly 账号的只读视角呈现，排查结论与自查步骤见 D0 文档第五节，本轮容器侧零开发）。

**与既有模块的分界（D1 AA 附录B）**：应用档案与生命周期=本模块；Python 运行环境本体=env-mgmt（环境软件包层）；应用服务单元的通用清单治理=service-mgmt（双入口并存 ⚠️A12）；反向代理站点本体（域名/HTTPS/证书）=site-mgmt（本模块消费建站能力）；应用代码放置=file-manager/终端（本模块仅校验存在性）；应用所需数据库=database-mgmt 既有能力自建。服务对象：管理员（admin）执行全部操作与日志查看；只读用户（readonly）查看应用清单与任务（ADR-018），**日志内容 admin 专属**（⚠️A8，沿数据库数据内容先例）。

## 第三部分：角色定义（G3）

| 角色 | 英文 | 职责与权限 | 获得方式 |
|------|------|-----------|---------|
| 管理员 | admin | 查看应用全景与任务 + 全部变更类操作（创建/依赖安装/删除/服务操作/参数编辑/建站联动）+ 应用日志查看 | account-auth 初始化/用户管理创建 |
| 只读用户 | readonly | 同等查看应用列表（档案+实况）与任务状态/输出（ADR-018 全可看）；一切变更无入口 + 越界请求被全局边界管控拒绝；**应用日志不可见**（⚠️A8 日志 admin 专属，入口不渲染 + 数据内容接口拒绝） | 管理员创建并指派 |

访客（未认证操作者）不涉及：本模块全部功能位于登录会话之后（R-02）。角色差异边界：全部写类操作与日志查看为 admin 专属；查看类动作不写审计（R-03 语义为「变更」留痕）；异步任务终态由任务执行链写审计。

### 4.2 应用部署与变更（C-16）

| 编号 | 需求 | 主流程与规则 | 审计 |
|------|------|-------------|------|
| FR-03 | 应用创建（C-16-01） | 创建 Python 应用：①前置校验逐项如实（⚠️A1/A2/A4）——应用名唯一（格式约束 D3 定稿）/代码目录存在/入口文件存在/Python 环境就绪（FR-11，缺失分层呈现并引导环境管理）/端口冲突检测（本机监听查询，占用如实拒绝不静默换端口）；②发起即创建异步任务（pending，⚠️A3）并立即返回 taskId；③任务执行链：创建 venv（python3 -m venv，R-08 参数数组）→ 依赖安装（存在 requirements.txt 则 pip 安装，无清单跳过该步 ⚠️A11）→ 生成 systemd 服务单元（⚠️A4/A6）——FastAPI 预设：venv 内 uvicorn 入口 + 模块:实例参数模板（编译期常量）；自定义命令：venv 内相对路径白名单校验；默认绑 127.0.0.1（OUT-10）；Restart=on-failure；单元文件经安全写入管线落盘（备份→原子写→校验→失败回滚原字节，⚠️A6，沿 R-06 同构；单元命名前缀 D3 定稿）；④可选立即启动（服务操作通道）；⑤档案登记（app：名称/目录/入口/启动方式/端口/运行用户/单元引用）与任务终态同事务；外部命令一律字面量参数数组（R-08）；任务输出尾部与失败原因经 FR-06 呈现，不虚构成功 | app_task_started（创建任务）+ 任务终态审计（detail 含应用/动作，**不含环境变量值与启动参数值**） |

| FR-05 | 应用删除（C-16-03） | 删除应用：强确认交互——明示「代码目录将保留」，可选勾选「同时删除代码目录（含运行环境）」改变删除范围（⚠️A5 知情提示）；解除服务落位：停止服务 → 撤销开机自启 → 移除服务单元（安全管线回滚保障 ⚠️A6）→ 移除应用档案；**关联建站站点不自动删除**（呈现「站点仍在，请到站点管理自行处置」提示，⚠️A7）；**绝不静默删除用户代码**（保留为默认，删除为显式勾选）；异步任务执行；删除后应用回未登记态；未登记应用发起删除如实拒绝 | app_task_started + 任务终态审计（detail 含删除范围与知情提示呈现记录） |
| FR-06 | 应用变更任务跟踪（C-16-04） | 异步任务的观测与结果确认：任务状态 pending → running → succeeded / failed（⚠️A3）；呈现目标应用、动作（创建/依赖安装/删除）、发起者、发起时间、输出尾部（排障，行数上限编译期常量）、失败原因（依赖解析失败/网络失败/端口占用/环境缺失等如实分类，错误文本含 errcode data.reason 具体原因——沿 env-mgmt/db-tools worker 错误形态先例）；同应用在途任务互斥（pending/running 存在时新变更请求如实拒绝）；失败任务可重试（重试=重新执行依赖安装类步骤）；任务台账持久化（跨重启留存）；面板重启时在途 running 任务标 failed（如实呈现）；任务取消不做（OUT-8）；两角色可看（ADR-018） | 任务终态结果一并留痕（succeeded/failed 均记） |

### 4.3 应用运行与暴露（S-61）

## 第六部分：状态流转（T2）

**状态机：app_task（应用变更任务）四态状态机**（与 env_install_task/tool_deploy_task 同构 4/4）：

```
pending ──→ running ──→ succeeded（终态）
                └─────→ failed（终态，可重试=新任务或重试同任务 deps_install 类步骤）
面板重启恢复：running ──→ failed（error=面板重启中断，如实呈现）
```

- 任务动作维度（app_task_action）：create（创建）/deps_install（依赖安装）/delete（删除）——与状态独立（动作非状态）；
- 同应用在途互斥：pending/running 存在时同应用新变更请求如实拒绝；
- 终态不可逆：succeeded/failed 不可迁移；失败重试=重新执行依赖安装类步骤（create 失败的档案登记不生效可重新发起创建）。

**辨析（非状态机项）**：

| 项 | 判定 | 理由 |
|----|------|------|
| 应用服务运行态 | 非状态机 | systemd 单元实况投影（active/inactive/failed 三态透传），事实源在 systemd 侧，与 service_active_state 共享口径，面板不自持 |
| 应用档案存在性 | 非状态机 | 档案存在=已登记，删除=移除记录；无中间状态（创建中为任务态非档案态） |
| 依赖就绪度 | 非状态机 | 实况探测投影（Python 环境/venv/依赖三层布尔），事实源在包管理器与文件系统 |
| 建站状态 | 非状态机 | 站点存在性经 site-mgmt 清单联动查询呈现，本模块不持久化站点引用 |
| 任务状态 vs 服务状态 | 独立维度 | 任务台账记录变更动作执行事实；服务运行态为运行实况——「任务 succeeded 但服务未启动」合法（创建时未勾选立即启动），如实分开呈现 |
