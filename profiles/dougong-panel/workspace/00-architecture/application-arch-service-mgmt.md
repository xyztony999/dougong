## 第一部分：文档概述

### 1.1 背景与目标

将《斗拱面板 systemd 服务管理（service-mgmt）业务架构》（business-arch-service-mgmt.md v1.0）的 4 个 L3 关键业务按 DDD 四层归类为应用域，组织为功能模块/功能子模块，标注涉及用户类型与模块间调用关系，作为 PRD（D2）、API 设计（D3）与交互设计（D4）的功能组织依据。dbus 通道（sysd 适配器）选型为材料给定事实（R-08），具体实现归 D2/D3，本架构不涉及。

DDD 归类结论（依据 d1 分册归类原则逐条判定）：

- **核心业务域**：运行状态操作（active ⇄ inactive / failed 状态机，kb 拍板；启停/重启为本域管控主链核心动作）、开机自启管理（enabled ⇄ disabled 状态机，kb 拍板独立维度）——两者均承载本域核心管控价值且有明确状态机。说明：两状态机均为 systemd 侧状态的投影流转，systemd_service 以内存态投影对象承担（不落库，kb 拍板），D2 领域模型按「非持久化领域对象」建模，状态流转事实源在 systemd 侧；
- **支撑业务域**：服务发现与纳管（含 R-15「发现即接管」与实时投影不落库领域规则，被核心域与观测消费）、服务观测（含 unit 类型展示范围与过滤搜索口径领域规则）；
- **基础数据域**：本模块无基础数据 L3——systemd_service 是本模块业务对象本身而非系统级引用数据（实时投影、无状态机的「自有数据」），不归基础数据域；
- **平台支撑域**：本模块无零业务语义的纯技术 L3——dbus 调用通道（sysd 适配器）为技术实现细节（R-08），与 account-auth 对密码哈希的处理口径一致，不构成功能模块。

> 模块编码衔接说明（编码规则的跨模块执行口径）：功能模块编码全局唯一，承接 account-auth 已占用的 C-01~C-03、S-01~S-05，panel-core 已占用的 S-06~S-12，monitoring 已占用的 S-13~S-16；本模块核心业务域模块自 C-04 起编至 C-05，支撑业务域模块自 S-17 起编至 S-18（依据「新模块在域内最大序号后递增」）。

### 1.3 范围

| 范围 | 说明 |
|------|------|
| 业务域 | systemd 服务管理（service-mgmt） |
| 应用域 | 核心业务域（运行状态操作、开机自启管理）、支撑业务域（服务发现与纳管、服务观测） |
| 用户类型 | 管理员（admin）、只读用户（readonly） |

> 用户类型语义（与 account-auth/panel-core/monitoring 应用架构一致）：**管理员（admin）**——全部服务操作（启动/停止/重启/自启切换）的执行者；**只读用户（readonly）**——按 ADR-018「全模块可查看」同等查看服务列表、过滤搜索与 unit 属性，禁一切服务操作。**访客（未认证操作者）不涉及**：本模块全部功能位于登录会话之后，无任何访客触达点，故用户类型矩阵不含访客（与 monitoring 同口径）。

## 第二部分：应用架构

> 本章按应用域逐层描述功能模块与功能子模块。每个应用域有其概述，每个功能模块/子模块有功能说明及涉及用户类型。

### 本架构概览

应用架构按 DDD 四层聚为两个应用域：

- **核心业务域**承载管控主链：运行状态操作维持服务运行维度状态（启动/停止/重启，经操作任务等待终态反馈），开机自启管理维持自启维度状态（enable/disable 切换）；
- **支撑业务域**为主链提供输入与视野：服务发现与纳管经 dbus 实时读取 system 级管理器 unit 并自动纳管（无注册动作），服务观测消费纳管投影提供列表/过滤搜索/属性查看。

调用关系总脉络：纳管投影是列表与属性查看的数据源；观测视图是操作动作的入口与操作前状态依据；操作结果经投影刷新回到观测视图；全部变更类操作经 account-auth 审计契约留痕（R-03）；全部接口位于登录会话之后并受只读边界管控（account-auth S-03，全局中间件层面生效，不在本模块内单列调用）。跨模块契约与模块边界见附录B。

### 应用域分层

> 按 DDD 战略设计，将应用域归入不同分层，决定后续详细设计的建模深度和投入策略。AA 应用域严格按照 DDD 四层划分，每个 BA L3 按 L3→DDD 四层归类原则归入对应分层。

| 分层 | 说明 | 包含功能模块 |
|------|------|-------------|
| 核心业务域 | 承载核心业务价值，有状态机和聚合根，深度建模 | 运行状态操作（C-04）、开机自启管理（C-05） |
| 支撑业务域 | 为核心业务提供必要的业务支撑能力，包含业务规则，独立上下文 | 服务发现与纳管（S-17）、服务观测（S-18） |
| 基础数据域 | 系统级引用数据，无业务状态机，薄适配 | —（本模块无；systemd_service 为本模块业务对象本身的实时投影，非系统级引用数据） |
| 平台支撑域 | 纯技术能力，零业务语义，可复用 | —（本模块无；dbus 调用通道（sysd 适配器）为技术实现细节，R-08） |

### 2.1 核心业务域

**应用域概述**：承载 systemd 服务管控主链：运行状态操作维持服务的运行维度状态，开机自启管理维持服务的自启维度状态。服务的用户群体：管理员（admin）；只读用户（readonly）在本应用域无任何操作入口（ADR-018）。

#### 2.1.1 运行状态操作（C-04）

**功能说明**：运行维度状态机（active ⇄ inactive / failed）的管控能力：服务启动与停止、服务重启，经操作任务等待终态并反馈结果；操作对象仅 .service 类型 unit。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

##### 2.1.1.1 服务启动与停止（C-04-01）

**功能说明**：对 .service 类型 unit 执行启动（inactive/failed → active）与停止（active → inactive）；提交后等待执行终态并反馈结果；在途操作防重复提交。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 操作执行与结果反馈（C-04-03） | 启动/停止经操作任务通道提交并等待终态 |
| 审计记录（account-auth S-04） | 启动/停止为变更类操作，写审计（R-03） |

##### 2.1.1.2 服务重启（C-04-02）

**功能说明**：对 .service 类型 unit 执行重启；对 failed 状态服务是面板提供的首要恢复动作；提交后等待执行终态并反馈结果。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 操作执行与结果反馈（C-04-03） | 重启经操作任务通道提交并等待终态 |
| 审计记录（account-auth S-04） | 重启为变更类操作，写审计（R-03） |

##### 2.1.1.3 操作执行与结果反馈（C-04-03）

**功能说明**：启停/重启类操作的任务执行机制：提交 systemd 侧异步任务、等待完成、反馈终态（成功进入目标状态 / 失败呈现失败原因与失败后状态）；同步等待上限与超时口径归 D2/D3 细化（BA 2.3.1.3 业务结论：等待终态并如实反馈，不做「提交即成功」假反馈）。系统内部机制，无直接用户交互。

**涉及用户类型**：- [ ] 管理员（admin） - [ ] 只读用户（readonly）（系统内部机制，被 C-04-01/C-04-02 编排）

**调用关系**：

*（无调用，作为被启停/重启动作编排的任务执行通道）*

#### 2.1.2 开机自启管理（C-05）

**功能说明**：自启维度状态机（enabled ⇄ disabled）的管控能力，独立于运行维度：切换自启状态不改变当前运行状态。操作对象仅 .service 类型 unit。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

##### 2.1.2.1 开机自启切换（C-05-01）

**功能说明**：对 .service 类型 unit 在 enabled ⇄ disabled 间切换开机自启；切换即时生效，结果反映到列表自启列与属性视图；自启切换为轻量同步操作（无任务等待），结果反馈口径与 2.1.1.3 一致（等待执行结果并如实反馈）。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 审计记录（account-auth S-04） | 自启切换为变更类操作，写审计（R-03） |

### 2.2 支撑业务域

**应用域概述**：为管控主链提供输入与视野：服务发现与纳管维护「系统实况 → 面板视野」的自动投影通道，服务观测提供列表、过滤搜索与属性查看。服务的用户群体：管理员（admin）与只读用户（readonly）同等使用查看能力（ADR-018）。

#### 2.2.1 服务发现与纳管（S-17）

**功能说明**：system 级管理器 unit 的实时读取与自动纳管：清单发现（全 unit 类型）与纳管同步（发现即接管、不落库）。无任何用户发起的动作入口，为系统被动机制。

**涉及用户类型**：- [ ] 管理员（admin） - [ ] 只读用户（readonly）（系统被动机制，纳管结果经 S-18 呈现）

##### 2.2.1.1 存量 unit 清单发现（S-17-01）

**功能说明**：实时读取 system 级管理器全部 unit 清单（service/socket/timer/mount 等全部类型）：名称、类型、运行状态与 sub 状态、开机自启状态；经 dbus 标准接口，不拼接 shell（R-08）。单 unit 属性读取与清单发现同通道。

**涉及用户类型**：- [ ] 管理员（admin） - [ ] 只读用户（readonly）（系统被动机制）

**调用关系**：

*（无调用，作为服务列表与属性查看的数据源被消费）*

##### 2.2.1.2 服务自动纳管与同步（S-17-02）

**功能说明**：发现即接管（R-15）：unit 无需注册即出现在面板服务视野；新装 unit 自动出现、已卸载 unit 自动消失，服务集合与系统实况自动同步；systemd_service 为实时投影不落库，无幽灵条目。

**涉及用户类型**：- [ ] 管理员（admin） - [ ] 只读用户（readonly）（系统被动机制）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 存量 unit 清单发现（S-17-01） | 纳管与同步以清单发现结果为输入 |

#### 2.2.2 服务观测（S-18）

**功能说明**：纳管服务全集的查看能力：服务列表（名称/类型/运行状态/自启状态）、状态过滤与名称搜索、unit 基本属性查看；是操作动作的入口与操作前状态依据。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）

##### 2.2.2.1 服务列表查看（S-18-01）

**功能说明**：以列表呈现 system 级管理器全部 unit：名称、unit 类型、运行状态（active/inactive/failed + sub 状态）、开机自启状态；列表内容为实时投影，服务随系统安装/卸载自动进出列表。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 存量 unit 清单发现（S-17-01） | 列表内容为清单发现的实时投影（纳管同步语义见 S-17-02） |

##### 2.2.2.2 状态过滤与名称搜索（S-18-02）

**功能说明**：按运行状态（active/inactive/failed）过滤列表、按 unit 名称关键字搜索；支撑在大存量服务集中快速定位目标。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 服务列表查看（S-18-01） | 复用列表数据获取通道，在其结果上执行过滤与搜索 |

##### 2.2.2.3 unit 基本属性查看（S-18-03）

**功能说明**：查看单个 unit 的基本属性快照：描述、加载状态、运行状态与 sub 状态、开机自启状态、unit 类型；不含日志查看与 unit 文件编辑（D0 边界 OUT）。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 存量 unit 清单发现（S-17-01） | 单 unit 属性经清单发现同一 dbus 实时通道读取 |

```
│   └── 开机自启管理（C-05）
│       └── 开机自启切换（C-05-01） — enable ⇄ disable，独立于运行维度
├── 支撑业务域
│   ├── 服务发现与纳管（S-17）
│   │   ├── 存量 unit 清单发现（S-17-01） — system 级全部类型 unit 实时读取（机制型）
│   │   └── 服务自动纳管与同步（S-17-02） — 发现即接管、实时投影不落库（机制型）
│   └── 服务观测（S-18）
│       ├── 服务列表查看（S-18-01） — 名称/类型/运行状态/自启状态实时投影列表
│       ├── 状态过滤与名称搜索（S-18-02） — 按运行状态过滤 + 名称关键字搜索
│       └── unit 基本属性查看（S-18-03） — 单 unit 基本属性快照（不含日志/文件编辑）
├── 基础数据域
│   └── —（无；systemd_service 为本模块业务对象本身的实时投影，非系统级引用数据）
└── 平台支撑域
    └── —（无；dbus 调用通道（sysd 适配器）为技术实现细节，R-08）
```

### 附录B：跨模块契约与模块边界

**跨模块契约**：

| 契约 | 方向 | 内容 |
|------|------|------|
| 审计写入（account-auth S-04） | 本模块消费 | 全部服务操作（启动/停止/重启/自启切换）按 R-03 写入审计：谁、何时、对哪个 unit、执行了什么操作、结果 |
| 会话鉴权与只读边界（account-auth S-03） | 本模块消费 | 全部接口位于登录会话之后；只读角色按 ADR-018「全可看」同等查看、禁一切服务操作，越界请求被全局边界管控拒绝 |
| dbus 调用通道（sysd 适配器） | 本模块消费 | 本模块为 sysd 适配器的唯一业务消费模块；经 dbus 标准接口（R-08），不拼接 shell 命令 |

本模块为服务消费终模块：不向其他业务模块输出契约（monitoring 的进程 TOP、后续模块对 unit 状态的消费如出现，另行在对应模块设计中定义）。

**模块边界（OUT，沿 D0 结论）**：

| 事项 | 归属 |
|------|------|
| 进程 TOP 列表 | monitoring（S-14-02） |
| journalctl 服务日志查看 | MVP 不做，留二期（D0 边界 OUT） |
| unit 文件编辑 | 不做（D0 边界 OUT） |
| dbus 调用通道实现（sysd 适配器） | 后端工程实现（R-08 技术规约），不在业务/应用模块层 |
