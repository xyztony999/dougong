## 第一部分：文档概述

### 1.1 背景与目标

systemd 服务管理（service-mgmt）是斗拱面板「接管存量环境」哲学的最直接体现：服务器上已装的 systemd 服务不重装、不注册，自动纳入面板管理（规则 R-15）。面板自身也以一条 systemd 服务常驻（idea.md §5），本模块因此天然是管理员日常运维的高频入口。业务输入来源：idea.md §4.1 M2「systemd 服务列表/状态/启停/重启/开机自启开关」、D0 需求澄清报告（d0-clarification-service-mgmt.md，2026-11-12）、知识库对象 systemd_service 及其双维度状态机（active/inactive/failed + enabled/disabled）、规则 R-08（dbus 通道禁 shell 拼接）、R-15（存量自动发现）、ADR-008（仅主流 systemd 发行版）、ADR-018（只读边界，经账户与安全基座生效）、R-03（全变更审计，经账户与安全基座审计契约）。

本业务架构设计目标：

1. 以 L1-L4 层级刻画 systemd 服务管理「服务发现 → 服务观测 → 服务操作」的业务主线；
2. 将已拍板的业务规则与双维度状态机（运行维度 active ⇄ inactive / failed、自启维度 enabled ⇄ disabled，两维度相互独立）落到确定的业务活动节点上，并落定 D0 留给本阶段的两个细化口径（unit 范围口径、操作耗时反馈口径）；
3. 为应用架构（AA）与功能清单（FL）提供唯一业务依据。

### 1.4 范围

| 范围 | 说明 |
|------|------|
| 业务域 | systemd 服务管理（service-mgmt）：服务发现、服务观测、服务操作 |
| 业务阶段 | 服务发现阶段、服务观测阶段、服务操作阶段 |

边界声明（OUT，沿 D0 结论）：

- 进程 TOP 列表归系统监控（monitoring）业务域，不在本域 L1-L4 内；
- journalctl 服务日志查看：材料 M2 未列，MVP 不做，留二期；
- unit 文件编辑：材料未列，不做；
- dbus 调用通道（sysd 适配器）为零业务语义的技术实现（R-08），归后端工程实现，不构成业务活动；
- 平台前提（ADR-008）：本域仅适用于主流 systemd 发行版（Debian 11+、Ubuntu 20.04+、RHEL 9 系），非 systemd 发行版不在产品范围内。

## 第二部分：业务架构

> 本章按 L2→L3→L4 逐层描述业务架构。每层有其概述和业务说明。

### 本架构概览

systemd 服务管理遵循「发现即接管 → 看得清 → 管得住」的业务主线，划分为三个业务阶段：

- **服务发现阶段**：面板不创建、不安装、不注册任何服务；system 级管理器上已装的 unit 经系统总线实时读取并自动纳入面板服务视野，服务集合始终与系统实况同步（发现即接管，R-15）；
- **服务观测阶段**：管理员与只读用户对纳管服务全集的查看能力——服务列表（含运行状态与自启状态）、状态过滤与名称搜索、unit 基本属性查看；
- **服务操作阶段**：变更类管控动作——运行状态操作（启动/停止/重启，运行维度状态机 active ⇄ inactive / failed）与开机自启管理（enable ⇄ disable，自启维度状态机 enabled ⇄ disabled，独立于运行维度）。

三阶段为支撑依赖序而非严格时间序：服务发现为观测提供数据全集，观测为操作提供入口与操作前状态依据，操作结果经实时投影刷新回到观测视图；观测与操作在服务全生命周期内循环往复。全部变更类操作按 R-03 记入审计（经账户与安全基座审计契约，跨域约定见应用架构附录B），变更操作仅管理员可执行（ADR-018）。

### 2.1 服务发现阶段

**业务说明**：「发现即接管」核心卖点在本模块的落点。面板对 systemd 服务没有任何「新增/导入」业务动作——系统上已装的 unit 是服务的唯一来源；systemd_service 为 dbus 实时投影，面板不持久化服务清单，每次呈现均为 systemd 当前实况（kb 拍板「不落库」）。管理范围为 system 级管理器（D0 落定口径，不含 user 级管理器）。

##### 2.1.1 服务发现与纳管

**业务说明**：将系统上已装的 systemd unit 自动纳入面板服务管理的业务能力。所属 L2：服务发现阶段。纳管为被动自动行为：无注册、无导入、无扫描确认入口，纳管结果直接体现为面板服务列表的内容。

###### 2.1.1.1 存量 unit 清单发现

**业务说明**：实时读取 system 级管理器的全部 unit 清单：含 service、socket、timer、mount 等全部 unit 类型；清单内容含 unit 名称、unit 类型、运行状态（active/inactive/failed）与 sub 状态、开机自启状态。读取经系统总线标准接口完成，不拼接 shell 命令（R-08）。所属 L3：服务发现与纳管。

###### 2.1.1.2 服务自动纳管与同步

**业务说明**：发现即接管（R-15）：unit 无需任何注册动作即出现在面板服务列表；新安装服务的 unit 在下次读取时自动出现，已卸载/已停用服务的 unit 自动从列表消失——服务集合与系统实况自动同步，面板侧不存在服务台账，因此没有「面板有但系统没有」的幽灵条目。所属 L3：服务发现与纳管。

### 2.2 服务观测阶段

**业务说明**：对纳管服务全集的查看能力，是操作类动作的入口与状态依据。查看能力按 ADR-018「全模块可查看」对管理员与只读用户同等开放，是只读角色在本域的核心价值。

##### 2.2.1 服务观测

**业务说明**：服务列表、过滤搜索与 unit 属性查看三类查看业务。所属 L2：服务观测阶段。

###### 2.2.1.1 服务列表查看

**业务说明**：以列表呈现 system 级管理器全部 unit：名称、unit 类型、运行状态（active/inactive/failed 及 sub 状态）、开机自启状态（enabled/disabled）。列表为实时投影（见 2.1.1.2），服务随系统安装/卸载自动进出列表。所属 L3：服务观测。

###### 2.2.1.2 状态过滤与名称搜索

**业务说明**：在服务列表上按运行状态（active/inactive/failed）过滤、按 unit 名称关键字搜索，支撑管理员在大存量服务集（单机常见数十至上百个 unit）中快速定位目标。所属 L3：服务观测。

###### 2.2.1.3 unit 基本属性查看

**业务说明**：查看单个 unit 的基本属性快照：描述、加载状态、运行状态与 sub 状态、开机自启状态、unit 类型等。日志查看（journalctl）与 unit 文件编辑均不在本域（D0 边界 OUT，见 1.4）。所属 L3：服务观测。

### 2.3 服务操作阶段

**业务说明**：变更类管控动作，是本域业务主链的核心环节。约束：仅管理员可执行（ADR-018 禁变更）；操作对象仅 .service 类型 unit——列表含全部 unit 类型，但操作入口仅对 .service 开放（D0 留本阶段细化口径，本阶段落定）；全部操作记审计（R-03）；操作有耗时的（重启/停止类）须等待 systemd 侧执行完成并反馈最终结果，在途操作防重复提交（D0 留本阶段细化口径，本阶段落定）。

##### 2.3.1 运行状态操作

**业务说明**：运行维度状态机 active ⇄ inactive / failed 的管控业务（kb 拍板）：启动使服务进入 active，停止使服务回到 inactive，重启为「停止 + 启动」的组合动作（亦作为 failed 服务的恢复手段）；每次流转由 systemd 侧执行并反映到实时投影。

###### 2.3.1.1 服务启动与停止

**业务说明**：对 .service 类型 unit 执行启动（inactive/failed → active）与停止（active → inactive）；操作目标与操作前状态来自观测视图。所属 L3：运行状态操作。

###### 2.3.1.2 服务重启

**业务说明**：对 .service 类型 unit 执行重启（active ⇄ inactive / failed 均可发起，结果归于 active 或 failed）；对 failed 状态服务，重启是面板提供的首要恢复动作。所属 L3：运行状态操作。

###### 2.3.1.3 操作执行与结果反馈

**业务说明**：启停/重启类操作在 systemd 侧以异步任务方式执行，面板等待任务完成并反馈最终结果：成功则服务进入目标状态，失败则呈现失败原因与失败后状态（如仍为 failed）；操作在途期间该服务的操作入口置为进行中，防重复提交。同步等待的上限与超时口径归 PRD/API 设计细化（D0 待细化项的本阶段结论：业务上要求「等待终态并如实反馈」，不做「提交即成功」的假反馈）。所属 L3：运行状态操作。

##### 2.3.2 开机自启管理

**业务说明**：自启维度状态机 enabled ⇄ disabled 的管控业务（kb 拍板，独立于运行维度）：自启状态决定服务是否随系统开机启动，与当前是否正在运行互不影响——enable 不改变运行状态，disable 也不停止运行中的服务。

###### 2.3.2.1 开机自启切换

**业务说明**：对 .service 类型 unit 在 enabled ⇄ disabled 之间切换开机自启状态；切换即时生效，结果反映到列表自启列与属性视图。所属 L3：开机自启管理。

## 第三部分：业务架构树

> **由第二部分内容对应生成，第二部分任何变更必须同步更新本视图。** 结构：L1 > L2 > L3 > L4。

```
systemd 服务管理（service-mgmt）
├── 服务发现阶段
│   └── 服务发现与纳管
│       ├── 存量 unit 清单发现
│       └── 服务自动纳管与同步
├── 服务观测阶段
│   └── 服务观测
│       ├── 服务列表查看
│       ├── 状态过滤与名称搜索
│       └── unit 基本属性查看
└── 服务操作阶段
    ├── 运行状态操作
    │   ├── 服务启动与停止
    │   ├── 服务重启
    │   └── 操作执行与结果反馈
    └── 开机自启管理
        └── 开机自启切换
```

### 附录B：业务术语表

> 统一业务术语定义，后续领域对象命名以此为准。

| 术语 | 定义 | 备注 |
|------|------|------|
| systemd 服务（systemd_service） | system 级管理器上已装 unit 在面板中的投影对象：名称、运行状态、sub 状态、开机自启、unit 类型 | dbus 实时投影，面板不落库（kb 拍板） |
| system 级管理器 | 操作系统级的 systemd 实例（PID 1），区别于用户会话级（user）管理器 | 本域管理范围口径，D0 留本阶段落定 |
| 发现即接管 | 系统上已装服务自动纳入面板管理，不重装、不注册、不导入 | R-15，项目核心哲学 |
| 实时投影 | 面板呈现的服务状态均为读取时刻的 systemd 实况，不持久化、无台账 | 面板侧无「幽灵条目」 |
| unit 类型 | systemd unit 的类别：service、socket、timer、mount 等 | 列表含全部类型；操作入口仅 .service 开放 |
| 运行状态（active/inactive/failed） | unit 运行维度三态：active 运行中、inactive 已停止、failed 失败 | kb 状态机：active ⇄ inactive / failed |
| sub 状态 | 运行状态的细分描述（如 running、exited、dead） | 随运行状态一并展示 |
| 开机自启（enabled/disabled） | unit 自启维度两态：enabled 随开机启动、disabled 不随开机启动 | kb 状态机：enabled ⇄ disabled，独立于运行维度 |
| 操作任务（Job） | 一次启停/重启类操作在 systemd 侧的异步执行单元 | 面板等待其完成以反馈终态（见 2.3.1.3） |
| 服务操作 | 对 .service 的变更类动作：启动/停止/重启/自启切换 | 仅管理员（ADR-018），全部记审计（R-03） |
