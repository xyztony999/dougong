## 第一部分：文档概述

### 1.1 背景与目标

应用管理（app-mgmt）是斗拱面板的 Python 应用托管模块（2026-11-20 用户提出部署自有 Python 项目 nim-proxy 的场景，d0-clarification-app-mgmt-2026-11-20.md）：面板已具备环境软件包安装（env-mgmt）、站点与反向代理（site-mgmt）、systemd 服务管理（service-mgmt）、文件管理（file-manager）等积木，但用户部署一个长期运行的 Python 应用（FastAPI/uvicorn 类）仍需手工串起「装运行时 → 建 venv → 装依赖 → 写 systemd 服务 → 建反代站点 → 看日志」六步。本模块把这条链收拢为应用生命周期管理：**创建应用（目录校验 → venv → 依赖安装 → 生成服务）→ 运行管理（启停/自启/参数/日志）→ 对外暴露（建站联动）→ 删除（保守保全）**。

用户四项拍板（D0，2026-11-20）：

- **Q1 部署路线 = venv + systemd 为主**：Python 应用走 venv + systemd 路线，对外暴露复用建站反向代理；容器侧仅排查只读问题（排查结论与自查步骤见 D0 文档第五节，本轮零开发）；
- **Q2 Python 运行时供给 = env-mgmt 扩第九环境**：环境目录八环境 → 九环境（+python，沿 Node 增量先例——目录条目扩展非新业务活动），本模块经环境实况读契约消费依赖就绪度；
- **Q3 能力范围 = 四项全选**：应用生命周期基础（列表/创建/删除 + 环境变量与启动参数编辑）、venv 与依赖安装（任务化）、进程托管与自启（systemd）、日志查看 + 建站联动；
- **Q4 容器取证 = 有列表无操作列**：前后端链路核验无缺陷（操作列仅 admin 渲染，readonly 视角恰为「有清单无操作列」），指向登录账号实际角色为 readonly——容器侧本轮零改动。

业务输入来源：D0 澄清报告（四拍板 + 复用积木取证 + 容器排查结论）、nim-proxy 本体形态（FastAPI + uvicorn + requirements.txt + 手工 deploy.sh——典型 venv/systemd 应用）、既有模块边界（env-mgmt=环境软件包层、service-mgmt=通用 systemd 单元层、site-mgmt=站点层、file-manager=文件层）。

本业务架构设计目标：

1. 以 L1-L4 层级刻画「看得见应用 → 部署得上应用 → 运行管得好应用」的应用生命周期主线；
2. 将安全底线落到业务口径（应用默认仅本机监听、端口冲突检测、服务单元安全写入、删除绝不静默删代码、审计贯穿、零遥测）——安全架构显式成节（第二部分 2.4）；
3. 明确与既有四模块的边界与消费关系（运行时供给/服务单元通道/站点暴露/文件放置），为「六步手工链」提供一站式业务闭环；
4. 为应用架构（AA）与功能清单（FL）提供唯一业务依据。

> ⚠️假设（本设计新增，承接 D0 拍板与边界裁定，如裁剪需同步三文档）：
>
> - ⚠️A1 应用档案口径：应用=用户自部署的 Python 应用档案（名称、代码目录、入口文件、启动方式、监听端口、运行用户候选）；面板不分发应用代码——代码由用户经文件管理器/终端预先放置，创建时校验代码目录与入口文件存在（缺失如实拒绝，不虚构）；单机多应用并存，应用名全局唯一；应用扩展上限 MVP 不设硬限（资源约束归服务器本身）。**v1.1 扩展（容器化形态，D0 Q5）**：应用类型二选一——venv/systemd 形态（既有主线）或容器化形态（⚠️A13：面板生成单应用 compose.yml + dougong-app 归属标签，经 docker-mgmt Compose 创建通道落盘并自动 up -d；容器化应用无代码目录/入口文件校验，改为镜像必填校验；venv 探测/服务单元对容器化应用不适用）。
> - ⚠️A2 运行时前置口径：应用创建前置=Python 运行环境已装（env-mgmt 第九环境 python：python3 + venv 支撑 + pip；就绪度经环境实况读契约消费，单向进程内）；缺失时创建动作如实拒绝并给出到环境管理的安装引导（不虚构成功、不静默代装环境——沿 db-tools ⚠️A2 同判）。
> - ⚠️A3 异步任务口径：应用创建（venv 创建 + 依赖安装首装）与依赖重装为异步变更任务（pip 安装可达数分钟）：任务状态 pending → running → succeeded / failed；同应用同时至多一个在途变更任务（互斥）；失败原因与输出尾部如实呈现（含 data.reason 具体原因，沿 env-mgmt/db-tools worker 错误形态先例）；失败可重试（重试=重新执行依赖安装步骤）；任务取消 MVP 不做（OUT——中断态不安全，沿 env-mgmt ⚠️A3 同判）。
> - ⚠️A4 服务形态口径：一个应用 = 一个 systemd 服务单元（单应用单 unit，多进程拓扑 OUT）；启动方式二选一——框架预设（fastapi 预设：venv 内 uvicorn 启动入口 + app 模块:实例名参数模板）或自定义启动命令（venv 内解释器/可执行相对路径白名单校验）；unit 默认 Restart=on-failure（异常退出自动拉起）；监听端口默认绑定 127.0.0.1（对外暴露一律经建站反代，⚠️A7）；创建时端口冲突检测（已被占用如实拒绝）。
> - ⚠️A5 删除口径：删除应用=停服务 + 撤服务单元 + 撤开机自启 + 撤在面板登记的档案；关联建站站点**不自动删除**（呈现提示由用户自行处置，防误删生产站点）；代码目录与 venv **默认保留**（可选项「同时删除代码目录」默认关闭，强确认交互明示「代码目录将保留/将删除」）；绝不静默删除用户代码（沿 db-tools 卸载不删数据哲学）；删除动作审计留痕。
> - ⚠️A6 服务单元安全写入口径：unit 文件创建/更新（参数编辑触发）走安全写入管线——备份原文件 → 原子写 → systemd 校验 → 失败回滚原字节（沿 site-mgmt R-06 管线同构）；unit 写入位置为系统服务目录（编译期常量路径，归 D3 定稿）；unit 命名带面板前缀（区分用户自建单元）。
> - ⚠️A7 站点暴露口径：对外暴露唯一推荐路径=经 site-mgmt 创建 reverse_proxy 站点反代 127.0.0.1:{应用端口}（消费 site-mgmt 建站 OHS，单向进程内，契约归 D3）；域名绑定/HTTPS/安全入口约束沿 site-mgmt 与 panel-core 既有能力（本模块不重复建设）；删除应用不自动删站点（⚠️A5）；不建站则应用仅本机可达（如实呈现）。
> - ⚠️A8 角色口径：管理员（admin）可执行全部操作（创建/删除/依赖重装/服务操作/参数编辑/日志查看/建站联动）；只读用户（readonly）可查看应用清单、状态与变更任务（ADR-018 全模块可查看），**日志内容 admin 专属**（沿数据库 key 数据内容先例），全部变更入口负空间。
> - ⚠️A9 审计口径：应用创建/删除/依赖重装/服务操作（启停/重启/自启切换）/参数编辑/建站联动记审计（R-03 写动作同事务，detail 脱敏——不含环境变量值与启动参数值内容）；服务操作与任务终态结果一并留痕。
> - ⚠️A10 环境变量与参数口径：环境变量经应用目录 .env 文件承载（unit 以 EnvironmentFile 引用）；启动参数为 unit 启动命令组成（框架预设参数模板 + 用户自定义参数段）；.env 内容属用户自有应用配置（非面板托管密钥），admin 可查看与编辑（编辑动作审计，detail 不含值内容）；参数变更后需重启服务生效（如实提示，不自动重启）。
> - ⚠️A11 Python 版本口径：基于系统 python3 单版本（env-mgmt 目录条目供给，版本随发行版仓库）；多版本共存/自选版本 OUT（沿 PHP 多版本二期先例）；venv 基于系统 python3 创建；依赖钉版本经 requirements.txt（pip 索引为第三方通道，无 sha256 可言——版本约束由用户依赖清单负责，失败如实呈现，不虚构校验能力）。
> - ⚠️A12 与 service-mgmt 重叠口径：应用服务单元在 service-mgmt 服务列表如实可见（通用单元层不做遮挡）；服务操作双入口并存（app-mgmt 应用语义入口 + service-mgmt 通用单元入口）指向同一 systemctl 通道，操作结果一致；服务清单治理与全量单元观测仍归 service-mgmt；app-mgmt 止步应用语义层（venv/依赖/入口/端口/参数），不重复建设通用单元能力。

## 第二部分：业务架构

> 本章按 L2→L3→L4 逐层描述业务架构。每层有其概述和业务说明。

### 本架构概览

应用管理遵循「看得见应用 → 部署得上应用 → 运行管得好应用」的业务主线，按应用生命周期划分三个业务阶段：

- **应用观测阶段**：应用清单呈现（档案 + 实况合并视图）与应用实况探测（服务运行态/自启态/venv 与依赖就绪度/端口占用）——是供给与运行两阶段的共同数据底座；
- **应用供给阶段**：应用创建（目录校验 → venv → 依赖安装 → 服务生成，任务化）、依赖重装（任务化可重试）、应用删除（保守保全）、变更任务跟踪——改变应用档案与服务落位的变更主链；
- **应用运行阶段**：进程托管与自启（启停/重启/开机自启，复用服务单元通道）、应用参数编辑（.env 与启动参数，安全写回）、应用日志查看（admin 专属）、站点暴露联动（建站反代，消费 site-mgmt）——应用跑起来之后的日常运维能力。

三阶段为顺序依赖关系：观测产出实况 → 供给改变实况与落位 → 运行作用于已落位应用；观测同时为供给动作提供前置依据（Python 环境就绪度、端口占用、应用名唯一性）与运行动作提供状态依据（未运行才可启动、运行中才可停止）。

### 2.1 应用观测阶段

**业务说明**：应用全景的数据底座：用户应用的档案清单（⚠️A1）叠加运行时实况探测（服务运行态/自启态/依赖就绪度/端口监听）形成应用全景；观测结果是供给动作的前置依据（Python 环境就绪才可创建、端口空闲才可占用）与运行动作的状态依据（应用运行态驱动服务操作按钮可用性）。

##### 2.1.1 应用清单与实况

**业务说明**：用户应用档案与运行时实况的合并呈现能力。所属 L2：应用观测阶段。档案为面板登记的应用台账（名称/目录/入口/启动方式/端口），实况每请求实时探测（不缓存不虚构——沿 env-mgmt 环境实况与 db-tools 工具实况同哲学）。

###### 2.1.1.1 应用清单呈现

**业务说明**：呈现应用台账全景：应用名、代码目录、入口文件、启动方式（框架预设/自定义）、监听端口、服务运行态、开机自启态、依赖就绪度（Python 运行环境 + venv 存在 + 依赖已装）、在途任务标记、关联站点提示（已建站 → 站点链接；未建站 → 本机可达说明）；未创建应用呈现创建入口（admin）。所属 L3：应用清单与实况。

###### 2.1.1.2 应用实况探测

**业务说明**：逐应用探测实况：服务运行态与自启态（经服务单元通道查询，⚠️A12 通道复用）、venv 存在性与 Python 环境就绪度（消费 env-mgmt 环境实况读契约，⚠️A2）、依赖安装态（venv 内包环境查询）、端口监听态（本机监听查询）；探测为纯读操作，机制承载无独立入口。所属 L3：应用清单与实况。

### 2.2 应用供给阶段

**业务说明**：应用生命周期的变更主链：创建（目录校验 → venv → 依赖安装 → 服务单元生成，⚠️A1/A2/A4）、依赖重装（任务化可重试，⚠️A3）、删除（保守保全，⚠️A5）；全部变更动作任务化执行与审计留痕（R-03），外部命令一律参数数组（R-08），服务单元写入走安全管线（⚠️A6）。

##### 2.2.1 应用部署与变更

**业务说明**：应用供给的变更主链。所属 L2：应用供给阶段。创建/依赖重装/删除三动作共用异步任务通道与审计纪律；任务产出（输出尾部、失败原因含 data.reason）如实呈现，不虚构成功；服务单元生成与更新经安全写入管线（⚠️A6）。

###### 2.2.1.1 应用创建

**业务说明**：创建 Python 应用档案并落位运行环境：**v1.1 起应用形态二选一（⚠️A13）**——①venv/systemd 形态（既有主线）：前置校验（应用名唯一、代码目录存在、入口文件存在、Python 运行环境就绪——缺失如实拒绝并引导到环境管理，⚠️A1/A2；端口冲突检测，⚠️A4）→ 在应用目录创建 venv（python3 -m venv）→ 依赖安装（存在 requirements.txt 则 pip 安装，无依赖清单可跳过该步骤，⚠️A11）→ 生成 systemd 服务单元（框架预设或自定义启动命令，默认绑 127.0.0.1，Restart=on-failure，⚠️A4/A6）→ 可选立即启动；②容器化形态（⚠️A13，D0 Q5）：前置校验（应用名唯一、镜像必填；无代码目录/入口校验）→ 面板生成单应用 compose.yml（镜像/监听端口/环境变量/挂载/重启策略 + dougong-app 归属标签）→ 经 docker-mgmt Compose 项目创建通道落盘并自动 up -d → 容器即时进入 docker-mgmt 实况清单（归属标签区分，全网视图照常可见）。两形态均为异步任务，成功后档案生效；创建动作审计留痕。所属 L3：应用部署与变更。

###### 2.2.1.2 依赖安装

**业务说明**：对已创建应用重装/补装依赖（requirements.txt 变更后）：校验 venv 存在（venv 缺失如实拒绝并提示重建应用或先修复目录）；pip 安装任务化执行（输出尾部与失败原因如实呈现，可重试，⚠️A3/A11）；依赖安装完成不自动重启服务（依赖热替换风险，提示用户自行重启生效）；动作审计留痕。所属 L3：应用部署与变更。

###### 2.2.1.3 应用删除

**业务说明**：删除应用档案并解除服务落位（⚠️A5）：强确认交互（明示「代码目录将保留」或勾选「同时删除代码目录」的删除范围知情提示）；停服务 → 撤开机自启 → 撤服务单元 → 撤档案；关联建站站点不自动删除（呈现「站点仍在，请自行处置」提示，⚠️A7）；**绝不静默删除用户代码**（保留为默认，删除为显式勾选）；删除为异步任务（服务撤除与目录删除耗时），删除后应用回未登记态；动作审计留痕。所属 L3：应用部署与变更。

###### 2.2.1.4 应用变更任务跟踪

**业务说明**：异步任务的观测与结果确认：任务状态（pending → running → succeeded / failed，⚠️A3）、目标应用与动作（创建/依赖重装/删除）、输出尾部（排障）、失败原因（依赖解析失败/网络失败/端口占用/环境缺失等如实分类，含 data.reason 具体原因）；同应用在途任务互斥（重复提交如实拒绝）；失败任务可重试（重试=重新执行依赖安装类步骤）。所属 L3：应用部署与变更。

### 2.3 应用运行阶段

**业务说明**：已落位应用的日常运维能力：进程托管与自启（启停/重启/开机自启开关，⚠️A12 通道复用）、应用参数编辑（.env 与启动参数，安全写回与生效提示，⚠️A6/A10）、应用日志查看（admin 专属，⚠️A8）、站点暴露联动（建站反代，消费 site-mgmt，⚠️A7）；安全架构详见 2.4 专节。

##### 2.3.1 应用运行与暴露

**业务说明**：应用运行态管理与对外暴露的运维能力。所属 L2：应用运行阶段。服务操作复用服务单元通道（与 service-mgmt 双入口并存同结果，⚠️A12）；参数与单元文件变更走安全写入管线（⚠️A6）；对外暴露唯一推荐路径为建站反代（⚠️A7）。

###### 2.3.1.1 进程托管与自启

**业务说明**：应用服务的运行操作：启动/停止/重启（在途操作互斥，操作后状态如实刷新）、开机自启开关；操作经服务单元通道执行（⚠️A12，R-08 参数数组）；运行态异常（unit 存在但服务 failed）如实呈现并提示查看日志；操作动作审计留痕（⚠️A9）。所属 L3：应用运行与暴露。

###### 2.3.1.2 应用参数编辑

**业务说明**：应用运行参数的查看与编辑：环境变量（.env 文件内容查看/编辑，admin 可见——用户自有应用配置非面板托管密钥，⚠️A10）与启动参数（框架预设参数段/自定义参数段）编辑；编辑经安全写入管线落盘（.env 原子写备份；unit 参数变更触发单元文件更新，⚠️A6）；变更后需重启服务生效（如实提示，不自动重启）；编辑动作审计留痕（detail 不含参数值，⚠️A9）。所属 L3：应用运行与暴露。

###### 2.3.1.3 应用日志查看

**业务说明**：应用运行日志的尾部查看（经系统日志通道查询本应用服务单元日志，R-08 参数数组）：档位选择（尾部行数），内容 admin 专属（⚠️A8，readonly 负空间）；日志只读呈现不提供清理动作（系统日志轮转归系统自身机制）。所属 L3：应用运行与暴露。

###### 2.3.1.4 站点暴露联动

**业务说明**：应用对外暴露的建站联动：一键创建反向代理站点反代 127.0.0.1:{应用端口}（消费 site-mgmt 建站能力，单向进程内，⚠️A7）；可选填写域名（域名绑定/HTTPS 沿 site-mgmt 与 panel-core 既有能力，本模块不重复建设）；已建站应用呈现站点链接与「前往站点管理」引导；删除应用不自动删站点（⚠️A5）；联动动作审计留痕（⚠️A9）。所属 L3：应用运行与暴露。

### 2.4 安全架构（显式专节，不可妥协底线）

> 本节为 D0 安全底线的业务架构落点，与 2.2/2.3 各 L4 互为表里。**本节为横切安全专节，非 L2 业务阶段**（L2 仅 2.1~2.3 三阶段，业务架构树不含本节）。任何裁剪不得削弱本节约束。

**防线一：网络面收敛（本机监听，⚠️A4/A7）**

- 应用进程默认绑定 127.0.0.1（unit 启动参数模板强制携带监听地址；自定义命令场景创建时校验监听地址参数，公网绑定需显式改参并自行承担暴露风险——面板不主动生成公网绑定配置）；
- 应用不注册任何防火墙放行规则（对外暴露一律经面板建站反代，⚠️A7）；
- 端口冲突检测贯穿创建（已被占用如实拒绝，不静默换端口）。

**防线二：变更安全（⚠️A3/A6/A9，R-03/R-08）**

- 外部命令（python3/pip/systemctl/日志查询）一律字面量参数数组（R-08），应用名/路径/参数经白名单与规范化校验（防注入：应用名格式约束、目录路径约束、启动命令相对 venv 白名单校验）；
- 服务单元与 .env 写入走安全管线（备份 → 原子写 → 校验 → 失败回滚原字节，⚠️A6，沿 R-06 同构）——不产生半配置；
- 写动作（创建/删除/依赖重装/服务操作/参数编辑/建站联动）同事务审计脱敏（R-03，detail 不含环境变量值与启动参数值）。

**防线三：删除保守与数据保全（⚠️A5）**

- 删除应用绝不静默删除用户代码（保留为默认，删除为显式勾选 + 强确认知情提示）；
- 关联站点不自动删除（提示用户自行处置，防误删生产站点）；
- venv/依赖删除仅随「同时删除代码目录」显式勾选发生。

**防线四：角色边界与零遥测（⚠️A8/A9，R-09）**

- readonly 可看清单/状态/任务，日志内容 admin 专属（沿数据库 key 数据内容先例），全部变更入口负空间（ADR-018）；
- 全部接口位于登录会话之后（会话校验/角色校验沿 account-auth 既有全局中间件，本模块不自建会话）；
- 零遥测（R-09）：pip 安装为用户主动发起的第三方索引访问（用户依赖清单驱动，面板自身不主动外呼）。

## 第三部分：业务架构树

> **由第二部分内容对应生成，第二部分任何变更必须同步更新本视图。** 结构：L1 > L2 > L3 > L4。

```
应用管理（app-mgmt）
├── 应用观测阶段
│   └── 应用清单与实况
│       ├── 应用清单呈现
│       └── 应用实况探测
├── 应用供给阶段
│   └── 应用部署与变更
│       ├── 应用创建
│       ├── 依赖安装
│       ├── 应用删除
│       └── 应用变更任务跟踪
└── 应用运行阶段
    └── 应用运行与暴露
        ├── 进程托管与自启
        ├── 应用参数编辑
        ├── 应用日志查看
        └── 站点暴露联动
```

### 附录A：L3 业务依赖关系

> 描述 L3 关键业务之间的上下游依赖关系，为后续应用架构中模块调用分析提供依据。

| 上游 L3 | 依赖方向 | 下游 L3 | 依赖说明 |
|---------|---------|---------|---------|
| 应用清单与实况 | → | 应用部署与变更 | 实况（环境就绪度/端口占用/应用名唯一性/venv 存在性）是创建/依赖重装/删除的前置依据 |
| 应用部署与变更 | → | 应用清单与实况 | 变更任务完成后实况与档案刷新（创建/删除改变台账） |
| 应用清单与实况 | → | 应用运行与暴露 | 运行态是服务操作按钮可用性的状态依据（未运行才可启动） |
| 应用部署与变更 | → | 应用运行与暴露 | 供给产出（服务单元/venv/参数文件）是运行操作与参数编辑的对象 |
| 应用清单与实况 | → | env-mgmt（他域） | 消费环境实况读契约（Python 运行环境就绪度：python3/venv/pip 已装态，进程内单向） |
| 应用部署与变更 | → | env-mgmt（他域） | Python 环境为本轮 env-mgmt 增量供给（第九环境）；依赖缺失时引导到环境管理安装（软引导） |
| 应用运行与暴露 | → | site-mgmt（他域） | 站点暴露联动消费建站能力（reverse_proxy 站点反代 127.0.0.1:端口，进程内单向）；已建站呈现站点链接 |
| 应用运行与暴露 | → | service-mgmt（他域） | 服务操作复用 systemd 单元通道（SysdGateway 同源；双入口并存同结果，⚠️A12）；服务清单治理仍归 service-mgmt |
| 应用部署与变更 | → | account-auth（他域） | 全部变更动作写审计（R-03 同事务脱敏） |
| 应用运行与暴露 | → | file-manager（他域，弱关联） | 应用代码放置引导（创建时目录/入口校验缺失提示经文件管理器放置；无跨模块硬调用） |

## 增量 v2.0（2026-11-23）：宝塔式重组——运行时项目托管

> 依据 ADR-033 与 baota-restructure-design-2026-11-23.md 第三、四章。本节是 v2.0 的权威增量；上文 v1.1 中「容器化应用」相关表述以本节为准。

- **范围修订**：模块定位收窄为「非容器化的运行时项目托管」。OUT：容器运行形态（自 v0.3.0 起不可用，按部署形态二分下线，D-app-04）。IN：Node 项目托管（D-app-02）。
- **业务活动**：零新 L4。C-16-01 应用创建扩「运行时二选一（Python / Node）」，容器形态分支移除；C-16-02 依赖安装扩 Node 的 npm install；S-60-01 应用列表增运行时列与 Node 就绪度呈现。
- **页面归属**：应用管理不再是独立菜单，作为「网站管理 › Python 项目 / Node 项目」分栏呈现（由 site-mgmt 页面承载，路由 /app 重定向）。
- **跨模块消费**：新增消费 env-mgmt NodeReadiness；对 docker-mgmt Compose 创建通道的消费随容器形态下线。
