## 2. 现象（真实浏览器实测）

隔离实例（v0.4.0 构建）用面板自己的接口开启安全入口（入口路径 `0BhXOwHtKWdIc5nZ`），无头 Edge 打开 `http://127.0.0.1:18697/0BhXOwHtKWdIc5nZ/`：

| 请求 | 结果 |
|------|------|
| `GET /0BhXOwHtKWdIc5nZ/` | 200，`text/html`，入口 HTML |
| `GET /assets/index-B6IoHWbq.js`（入口 HTML 里引用的脚本） | **404** |
| `GET /favicon.svg` | 404 |

页面 `#app` 子节点数为 0、可见文字为空——白屏。不是个别环境的问题：任何人开启都会白屏。

## 3. 根因

| # | 事实 | 位置（main=273fb5f 时取证，行号随第一轮改动略有偏移） |
|---|------|------|
| 1 | 入口网关：开启后，请求路径必须是 `/{entryPath}` 或 `/{entryPath}/…`（剥前缀后交给后端）；其余一律标准 404。只有两个内部端点豁免 | `backend/internal/api/middleware/entrypath.go:34-64` |
| 2 | 入口 HTML 原样下发 | `backend/internal/api/server.go` serveSPA |
| 3 | 入口 HTML 引用的是**根路径**：`/assets/index-*.js`、`/favicon.svg`；构建工具未配置 `base`（默认 `/`） | `frontend/dist/index.html`、`frontend/vite.config.ts` |
| 4 | 前端接口地址 210 处全部是根路径写法，最终都汇到少数构造点（见 3.1） | `frontend/src/api/*.ts` |
| 5 | 路由的历史基址是 `/` | `frontend/src/router/index.ts`（`createWebHistory()`） |

也就是说：网关要求一切请求带入口前缀，而前端发出的请求全都不带——除了入口 HTML 本身，没有任何一个请求能通过。

## 4. 文档层面的缺口（已核对）

- PageSpec 声明「前端不感知 `/{entryPath}` 前缀：**静态资源与 API 均相对路径**」（`02-detailed/interaction/admin/panel-core/panel-core.md` 第 7 节「安全入口前缀」行）——设计意图是**一切都在入口路径之下、前端用相对地址**。实现从未做到，而验收没有发现。
- 验收只到 HTTP 级：`backend/internal/api/panel/module_test.go` 的 `TestEntryPathGuardOverHTTP` 只用带 / 不带前缀的**接口**请求验证网关本身；当时的 Gate 2 报告以这些用例为依据，没有在浏览器里开着入口路径把页面走通。

### 4.1 取证时的新发现：在设置页里「开启」这个动作本身就会弄坏当前页面

`EntryPathCard.vue`：开启成功后立刻 `panelStore.loadConfig()` 重新读取配置——这次请求不带前缀，被网关 404；「重新生成」同理（旧前缀立即失效，当前页面的后续请求全部 404）。关闭时反过来：页面是从 `/旧入口/…` 打开的，关闭后网关不再剥前缀，`/旧入口/assets/…` 落到深链兜底返回 index.html，而新版前端（如果修好了）的基址会变成 `/`。所以无论选哪个方案，开启 / 重新生成 / 关闭之后都必须让浏览器整页跳到正确的地址。

## 6. 候选方案（待用户拍板）

### 方案 A：完整前缀（贴近现有设计文档）

页面、脚本、图标、接口、WebSocket 全部位于入口路径之下；网关保持「不带前缀一律 404」。

做法要点：
- 构建工具改为相对地址（`base: './'`），入口 HTML 引用 `./assets/…`，按需加载的分包相对脚本自身解析，天然落在入口路径下。
- 服务端下发入口 HTML 时注入 `<base href="/{entryPath}/">`（未开启时 `/`），使深链接（`/{entryPath}/sites/12/source`）下的相对地址也解析正确。
- 路由历史基址、5 处集中请求、1 处直接请求、2 个 WebSocket 地址、4 处图标、第一轮的探测与自动重新加载，统一从一个「应用基址」辅助函数取前缀。
- 开启 / 重新生成后整页跳到新入口地址；关闭后整页跳到根地址。

| 优点 | 代价 |
|------|------|
| 安全模型不变：地址栏始终带入口路径，不带前缀的请求一律 404；与接口文档、PageSpec 的表述一致，不需要改安全口径 | 改动面较大（服务端注入 + 前端约 15 个构造点 + 构建配置），要逐项做浏览器级验证 |
| 不依赖浏览器 Cookie | 深链接、书签必须带入口路径（丢了前缀看到 404，属设计内的安全行为） |

### 方案 B：入口当作门（改动小，安全口径有变化）

入口路径只在「进门」时校验：访问正确的入口地址后，网关给浏览器发一个带签名的标记 Cookie；之后的脚本、接口请求只要带着这个标记就放行，地址保持在根路径。前端几乎不用改。

| 优点 | 代价 |
|------|------|
| 前端零改动或极少改动；地址栏不再暴露入口路径；深链接、书签都在根路径 | **安全口径变了**：由「不带前缀一律 404」变成「没有入口标记一律 404」，接口文档与 PageSpec 的表述要重写 |
| | 依赖浏览器 Cookie：禁用 Cookie 时开着入口路径的面板无法使用 |
| | 标记 Cookie 会留在浏览器里，同一台电脑的下一个人不经入口也能看到登录页（仍需账号密码）；要让入口重新生效需清除 Cookie 或重新生成入口路径 |
| | 服务端要新增带签名的 Cookie 签发与校验、入口路径变更时的失效处理 |

### 不采用的方案

- **只放行 `/assets/*` 与图标、接口仍要求前缀**：脚本文件 anyone 可取，暴露「这是一台斗拱面板」的指纹，削弱防探测；而前端该改的接口地址一处也少不了。不如方案 A。
- **把入口 HTML 改写成带前缀的绝对地址、构建配置不动**：构建工具对按需加载的样式表仍按根路径解析（`/assets/x.css`），会 404；而且每次构建产物变化都要跟着调改写规则。

### 推荐

**方案 A**。它是在还现有设计的账：接口文档与 PageSpec 早就写的是「一切在入口路径之下」，网关也已经按此实现并经过 HTTP 级验证；改动虽然多但都在少数几个构造点上，并且有浏览器级验收兜底。方案 B 改动小，但它改的是安全口径，还引入对 Cookie 的依赖，这些应该由用户明确选择而不是为了省事。

### 8.3 如实声明的边界与未覆盖项

- **终端 WebSocket 在本机无法完成握手**：Windows 开发机的终端后端创建不了进程（`TERM_004「终端进程创建失败」`，Unix PTY 平台限制）。对照实验（`ws-control.cjs`）：入口路径下与根路径都返回同样的 TERM_004，且入口路径下能通过鉴权、到达终端模块（不是被网关 404 拦掉）——**与本轮修复无关**。浏览器里确认了 WS 地址正确走在入口路径之下（`/{entryPath}/terminal/session/connect?identitySource=panel_run_user`）。真实终端会话归 Linux 目标环境冒烟。
- **日志跟随 WebSocket 未在浏览器实测**：验收实例上 Docker Desktop 未运行（不自行启动），无容器可跟随。其地址构造与终端 WS 同一封装（`dockerWsUrl` 经 `withBase`），由单测覆盖；网关侧路由与终端 WS 同口径。
- **W1（承第一轮固有边界）**：升级到含本修复的版本时，升级前已打开的旧页面仍需手动刷新一次——旧页面引用的分包文件名已不存在，且旧版本前端不含本修复。CHANGELOG 须注明「升级后请刷新一次已打开的面板页面」。
- **只读角色未在浏览器单独核对**（承第一轮 W5）；只测了 Chromium 内核（无头 Edge）。
- 域名绑定 HostGuard 与数据库工具内部端点豁免：代码未改动，HTTP 层核对内部端点豁免在入口开启时照常可达；HostGuard 链序（Entry→Host→gin）未动。
