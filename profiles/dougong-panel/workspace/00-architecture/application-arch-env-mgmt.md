## 第一部分：文档概述

### 1.1 背景与目标

将《斗拱面板 环境管理（env-mgmt）业务架构》（business-arch-env-mgmt.md v1.2）的 3 个 L3 关键业务按 DDD 四层归类为应用域，组织为功能模块/功能子模块，标注涉及用户类型与模块间调用关系，作为 PRD（D2）、API 设计（D3）与交互设计（D4）的功能组织依据。包管理器调用（apt/dnf·yum，R-08 参数数组）与 systemd 通道为技术实现承载，其业务纪律（强确认/审计/幂等，⚠️A2~A6）落在本架构的模块说明中，实现归 D3 与后端工程。**v1.1 安装后配置就绪增量**：新增功能子模块 C-14-04（机制型）——数据库类环境安装成功后经 database-mgmt 进程内 OHS 自动建管理账户/设密码并注册实例与凭据（装完即可管，⚠️A11~A15）。**v1.2 Node 环境增量**（db-tools 集成联动，D0 拍板 2026-11-19）：环境目录七→八条目（+Node.js，⚠️A1/A16）——NodeSource 三系代配 + LTS 轨道钉死 + npm 随包；Node 为运行时型环境（无服务单元，服务态 null/启停自启入口禁用，⚠️A17）；**无新功能模块/子模块**（Node 为目录条目非新 L3/L4，DDD 归类与编码集合零变化），S-53/S-54/C-14 既有子模块口径同步；新增 db-tools 被消费契约（环境实况读契约 + Node 供给）。**v1.3 Python 环境增量**（app-mgmt 集成联动，D0 拍板 2026-11-20）：环境目录八→九条目（+Python，⚠️A1/A18）——发行版仓库包（无第三方源代配，apt python3/python3-venv/python3-pip 三包候选·rpm python3）+ python3 --version 查询 + venv/pip 能力位探测；Python 为运行时型环境（⚠️A17 同构，服务态 null/启停自启入口禁用）；**无新功能模块/子模块**（目录条目非新 L3/L4，DDD 归类与编码集合零变化）；新增 app-mgmt 被消费契约（环境实况读契约 + Python 供给）。

DDD 归类结论（依据 d1 分册归类原则逐条判定）：

- **核心业务域**：环境安装与变更（承载 env_install_task 聚合根候选与四态任务状态机 pending → running → succeeded/failed，是环境供给的单据型主链动作，审计与互斥业务规则齐备）——满足原则一（状态机 + 聚合根候选 + 主链变更动作 + 产生任务记录）；
- **支撑业务域**：环境目录与实况（含目录范围/包名映射/通道探测领域规则，被供给与运行两链消费）、环境服务运维（含目录环境单元限定与结果如实反馈规则，复用 systemd 通道）——两者含运维领域特有业务规则、被主链消费，自身无独立状态机（服务启停状态为 systemd 实况投影非面板状态机）；
- **基础数据域**：本模块无基础数据 L3——环境目录虽为内置静态引用数据，但其 L3 整体含实况探测运行时规则（非纯字典），按整体归类支撑业务域（与 site-mgmt「PHP-FPM pool 实况投影不建基础数据 L3」同判）；
- **平台支撑域**：本模块无零业务语义的纯技术 L3——包管理器执行器与 systemd 通道为实现细节（前者本模块自建适配层，后者复用 service-mgmt 既有 SysdGateway 通道资产），业务规则承载于 S-53/C-14/S-54。

> env_install_task（环境变更任务）为本模块聚合根候选（四态状态机 + 同环境互斥 + 审计单据），持久化口径（任务台账落库）归 D2 领域建模落定；环境目录为编译期常量（非领域对象候选）。

> 模块编码衔接说明（编码规则的跨模块执行口径）：功能模块编码全局唯一，承接既有占用——account-auth C-01~C-03/S-01~S-05、panel-core S-06~S-12、monitoring S-13~S-16、service-mgmt C-04~C-05/S-17~S-18、file-manager C-06/S-19~S-25、site-mgmt C-07~C-10/S-26~S-30、database-mgmt S-31~S-37、terminal C-11/S-38~S-41、firewall S-42~S-44、docker-mgmt C-12/S-45~S-50、cron-backup C-13/S-51~S-52；本模块核心业务域模块编为 C-14，支撑业务域模块自 S-53 起编至 S-54（依据「新模块在域内最大序号后递增」）。

## 第二部分：应用架构

> 本章按应用域逐层描述功能模块与功能子模块。每个应用域有其概述，每个功能模块/子模块有功能说明及涉及用户类型。

### 本架构概览

应用架构按 DDD 四层聚为两个应用域：

- **核心业务域**承载环境供给状态链：环境安装与变更维持 env_install_task 四态任务状态机（pending → running → succeeded/failed，同环境互斥），安装/升级/卸载三动作共用任务通道与审计纪律；
- **支撑业务域**承载「看得见 + 管得住」：环境目录与实况以内置目录叠加实时探测供给环境全景（供给与运行的共同数据底座），环境服务运维提供目录环境的服务直达管控（复用 systemd 通道）。

调用关系总脉络：实况探测结果是安装/卸载/启停按钮态的前置依据；变更任务完成后实况刷新；服务运维作用于已装环境单元；环境未装实况为 docker-mgmt/database-mgmt/site-mgmt 引导态提供软引导数据（边界见附录B）；**数据库类环境安装成功后经 C-14-04 消费 database-mgmt 进程内 OHS（BootstrapAfterInstall）注册实例与凭据——v1.1 新增跨模块硬依赖（单向，装完即可管，⚠️A11/A12）**；全部变更类操作经 account-auth 审计契约留痕（R-03）；全部接口位于登录会话之后并受只读边界管控（ADR-018）。

### 应用域分层

> 按 DDD 战略设计，将应用域归入不同分层，决定后续详细设计的建模深度和投入策略。AA 应用域严格按照 DDD 四层划分，每个 BA L3 按 L3→DDD 四层归类原则归入对应分层。

| 分层 | 说明 | 包含功能模块 |
|------|------|-------------|
| 核心业务域 | 承载核心业务价值，有状态机和聚合根，深度建模 | 环境安装与变更（C-14） |
| 支撑业务域 | 为核心业务提供必要的业务支撑能力，包含业务规则，独立上下文 | 环境目录与实况（S-53）、环境服务运维（S-54） |
| 基础数据域 | 系统级引用数据，无业务状态机，薄适配 | —（本模块无；环境目录为编译期常量随 S-53 承载，实况为运行时投影，二者不构成独立基础数据 L3） |
| 平台支撑域 | 纯技术能力，零业务语义，可复用 | —（本模块无；包管理器执行器为本模块适配层实现、systemd 通道复用 service-mgmt 既有 SysdGateway 资产，业务规则承载于 S-53/C-14/S-54） |

### 2.1 核心业务域

**应用域概述**：承载环境供给的变更主链与任务状态机：安装/升级/卸载经异步任务执行（互斥、审计、输出如实），任务记录构成环境变更的可追溯台账。服务的用户群体：管理员（admin）执行全部变更；只读用户（readonly）仅可查看任务状态与输出（ADR-018）。

#### 2.1.1 环境安装与变更（C-14）

**功能说明**：环境本体的供给主链：安装与升级（同通道幂等，先刷新索引）、卸载（强确认+风险提示）、异步任务跟踪（四态状态机，输出尾部排障）、**安装后配置就绪（数据库类环境安装成功后自动引导，C-14-04 机制型）**；安全纪律贯穿（参数数组 R-08、审计 R-03、幂等、最小权限、引导凭据密文零回显）。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（变更动作仅管理员，任务状态与输出两角色可看）

##### 2.1.1.1 环境安装与升级（C-14-01）

**功能说明**：安装目录环境：包管理器通道可用性前置（⚠️A2，不可用如实拒绝）；先刷新包索引再安装（已装环境同动作为升级，幂等，⚠️A4）；需官方仓库源的环境先由面板写入仓库配置（审计）再安装（⚠️A2；v1.2 +Node.js NodeSource 三系代配，LTS 轨道钉死，npm 随 nodejs 包，⚠️A16）；异步任务化执行（⚠️A3），完成后服务状态尊重包脚本默认（⚠️A5；数据库类引导路径可启动服务，⚠️A15；Node 运行时型无服务联动，⚠️A17）；**数据库类环境安装成功后衔接 C-14-04 安装后配置就绪**。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 环境实况探测（S-53-02） | 安装前置：未装态/通道可用性依据；已装态升级语义判定 |
| 环境变更任务跟踪（C-14-03） | 安装/升级动作产生异步任务，进度与结果经任务跟踪呈现 |

| 审计记录（account-auth S-04） | 安装/升级为变更类操作，写审计（R-03，含仓库源写入） |

##### 2.1.1.2 环境卸载（C-14-02）

**功能说明**：卸载已装环境：强确认交互呈现关联模块在用风险提示（Docker 容器/MySQL 纳管实例/nginx 站点，知情决策不硬阻断，⚠️A6）；执行包 remove（保留系统配置与数据目录）；异步任务化执行，卸载后环境回未装态。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 环境实况探测（S-53-02） | 卸载前置：已装态依据与风险提示数据（关联模块在用探测） |
| 环境变更任务跟踪（C-14-03） | 卸载动作产生异步任务 |

##### 2.1.1.3 环境变更任务跟踪（C-14-03）

**功能说明**：异步任务的观测与结果确认：任务状态（pending → running → succeeded/failed）、目标环境与动作、命令输出尾部（排障）、失败原因、**引导结果（bootstrap_status/note，⚠️A14）**；同环境在途互斥（重复提交如实拒绝，⚠️A3）；任务列表与单任务详情。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（ADR-018 全可看）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 审计记录（account-auth S-04） | 任务终态（成功/失败）结果一并留痕（R-03） |

##### 2.1.1.4 安装后配置就绪（C-14-04）

**功能说明**：数据库类环境（MySQL/Redis/MongoDB）安装/升级成功后的自动配置引导（机制型，无独立菜单入口，⚠️A11）：worker 后置步骤确保 DB 服务就绪（幂等 start，⚠️A15）→ 消费 database-mgmt 进程内 OHS（BootstrapAfterInstall）经引导通道建管理账户/设随机强密码（MySQL dougong@localhost 全权 / Redis requirepass / MongoDB admin root，⚠️A12）并注册实例与凭据（装完即可管）→ 引导结果（succeeded/failed/skipped）回传任务台账与输出尾部呈现（⚠️A14）；幂等保守不覆盖用户已有配置（⚠️A13）；引导审计留痕、密码密文零回显。PHP/nginx/Apache/Docker/Node 装完即用无引导（Node 为 v1.2 新增运行时型，⚠️A17）。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（系统自动机制，随安装触发；引导结果两角色可看，ADR-018）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 环境安装与升级（C-14-01） | 宿主：安装/升级成功后 worker 触发本机制 |
| 环境服务启停与自启（S-54-01）/ SysdGateway | 引导前确保 DB 服务 active（幂等 start，等待就绪） |
| database-mgmt 实例引导注册 OHS（BootstrapAfterInstall） | 建账户/设密码/注册实例与凭据归 database-mgmt 实例层（进程内 OHS，单向消费，⚠️A12）；引导结果回传 |
| 环境变更任务跟踪（C-14-03） | 引导结果（bootstrap_status/note）入任务台账与详情呈现 |
| 审计记录（account-auth S-04） | 引导动作审计留痕（R-03，detail 不含密码） |

### 2.2 支撑业务域

**应用域概述**：承载「看得见 + 管得住」：环境目录与实况供给环境全景（内置目录 + 实时探测，供给与运行的共同数据底座，关联模块引导数据源），环境服务运维提供已装环境的服务直达管控。服务的用户群体：管理员（admin）查看与执行；只读用户（readonly）同等查看（ADR-018），无任何变更入口。

#### 2.2.1 环境目录与实况（S-53）

**功能说明**：内置九环境目录（⚠️A1，v1.1 +MongoDB，v1.2 +Node.js，v1.3 +Python）与运行时实况（已装/版本/服务状态/自启/通道可用性，⚠️A2/A7/A9；Node/Python 运行时型服务态不适用 null，⚠️A17/A18）的合并呈现；纯读能力，是供给与运行两链的状态依据，也是 db-tools 与 app-mgmt 依赖就绪度的数据源（v1.2/v1.3 被消费）。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（ADR-018 全可看）

##### 2.2.1.1 环境目录呈现（S-53-01）

**功能说明**：环境全景列表：显示名、描述、关联模块提示、已装版本、服务状态、通道可用性、在途任务标记；未装环境呈现安装入口（admin），已装呈现升级/卸载/服务运维入口（Node 条目服务运维入口禁用——运行时型无常驻服务，⚠️A17，呈现「运行时环境无常驻服务」说明）。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（变更入口仅管理员可见，ADR-018 负空间）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 环境实况探测（S-53-02） | 列表条目的实况字段为探测结果投影 |

##### 2.2.1.2 环境实况探测（S-53-02）

**功能说明**：逐环境探测：已装与版本（包管理器查询，⚠️A7 映射；Node 版本经 node --version，⚠️A16；Python 版本经 python3 --version 且 venv/pip 能力位一并探测，⚠️A18）、服务运行/自启状态（systemd 单元查询；Node/Python 无服务单元，服务态字段不适用 null 如实呈现，⚠️A17/A18）、包管理器通道可用性（apt/dnf·yum 探测择一，⚠️A2）；纯读机制，被目录呈现/安装/卸载/服务运维共同消费，并被 db-tools（v1.2）与 app-mgmt（v1.3，Python 就绪度含 venv/pip 能力位）依赖就绪度消费（进程内读契约）。

**涉及用户类型**：- [ ] 管理员（admin） - [ ] 只读用户（readonly）（系统内部机制，结果经 S-53-01 等呈现）

#### 2.2.2 环境服务运维（S-54）

**功能说明**：已装环境的服务层管控：启动/停止/重启/自启开关，经 systemd 通道生效（复用 service-mgmt 既有 SysdGateway 通道资产，非模块间调用）；操作对象限定目录环境对应单元（⚠️A7）——运行时型环境 Node 无服务单元，不在操作对象集内（⚠️A17，v1.2）；细粒度全部单元治理归 service-mgmt。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）
