## 第一部分：文档概述

### 1.1 背景与目标

将《斗拱面板 容器管理（docker-mgmt）业务架构》（business-arch-docker-mgmt.md v1.0）的 7 个 L3 关键业务按 DDD 四层归类为应用域，组织为功能模块/功能子模块，标注涉及用户类型与模块间调用关系，作为 PRD（D2）、API 设计（D3）与交互设计（D4）的功能组织依据。dockerx 适配器（Docker 官方 Go SDK 客户端 + `docker compose` CLI 调用封装，含 R-08 参数数组纪律）为零业务语义的技术实现资产（idea.md §5.1 后端适配层、§5.3 技术选型），归后端工程，本架构不涉及。

DDD 归类结论（依据 d1 分册归类原则逐条判定）：

- **核心业务域**：容器生命周期管理（C-12）——容器承载面板可操作的生命周期状态机（running ⇄ stopped ⇄ paused + 过渡态，ADR-025 拍板、kb 状态机表容器行），启停/重启/暂停恢复/删除六类动作为容器运维主链环节，动作 × 状态可用性矩阵（BA 附录B）为该状态机的业务规则载体，状态迁移结果为容器观测与 Compose 治理的直接输入——满足原则一「有明确的生命周期状态机、主链环节」（与 service-mgmt C-04/C-05「systemd 服务状态机投影操作入核心域」、site-mgmt C-07「站点启停状态机」同判：状态机为 daemon 实况投影不影响主链判定，面板动作即状态迁移唯一入口）；
- **支撑业务域**：其余 6 个 L3 归入此层——Docker daemon 接管（R-15「识别即接管」领域规则 + 「未安装 ≠ 无容器」降级语义）、容器观测（实况投影只读呈现 + 日志/资源口径）、镜像/卷/网络管理（daemon 实况 CRUD + 引用约束语义）、Compose 项目治理（label 识别规则 + `docker compose` CLI 编排口径 ADR-013/R-13，docker 运维领域特有业务规则）——均含本领域特有业务规则、支撑「接管存量环境」核心价值，但对象均无面板操作映射的自有状态机主链（compose_project 为 label 聚合派生投影，kb 状态机表无条目；镜像/卷/网络有无即状态），不满足原则一；
- **基础数据域**：无——镜像/卷/网络虽呈清单，但为 daemon 实况投影（随面板外变更实时漂移、面板不落库），不是面板维护、读远大于写的系统级引用数据，不满足原则三（与 firewall 对 firewall_rule 的辨析同判）；
- **平台支撑域**：无——dockerx 适配器为纯技术通道资产（零业务语义，换一个领域仍可用），但「接管哪个 daemon、状态怎么映射、动作矩阵怎么约束、label 怎么识别、CLI 怎么编排」均为容器运维领域业务语义且已承载于上述功能模块；按归类边界关键问题自检（该功能是否含本领域特有业务规则）→ 适配器不含 → 归实现细节，不构成功能模块（与 firewall 对 firewallx、database-mgmt 对 dbmysql/dbredis、service-mgmt 对 sysd 的处理口径一致）。

> 领域建模起步提示（供 D2）：container / image / volume / network 为无持久化的 daemon 实况投影对象候选（零持久化、无面板自有聚合根——与 firewall firewall_rule 同构）；compose_project 为容器 label 聚合的派生投影（无自有状态机）；容器状态机（ADR-025）为 daemon 实况的面板动作映射，不构成面板自持有状态。

> 模块编码衔接说明（编码规则的跨模块执行口径）：功能模块编码全局唯一，承接 account-auth 已占用的 C-01~C-03、S-01~S-05，panel-core 已占用的 S-06~S-12，monitoring 已占用的 S-13~S-16，service-mgmt 已占用的 C-04~C-05、S-17~S-18，file-manager 已占用的 C-06、S-19~S-25，site-mgmt 已占用的 C-07~C-10、S-26~S-30，database-mgmt 已占用的 S-31~S-37，terminal 已占用的 C-11、S-38~S-41，firewall 已占用的 S-42~S-44；本模块核心业务域 1 个模块编 C-12，支撑业务域 6 个模块自 S-45 起编至 S-50（依据「新模块在域内最大序号后递增」）。

## 第二部分：应用架构

> 本章按应用域逐层描述功能模块与功能子模块。每个应用域有其概述，每个功能模块/子模块有功能说明及涉及用户类型。

### 本架构概览

应用架构按 DDD 四层聚为两个应用域——**核心业务域**（容器生命周期管理 C-12）与**支撑业务域**（S-45~S-50），其下按「接入 → 观测 → 操作 → 资源 → 编排」组织 7 个功能模块：

- **接入线**：Docker daemon 接管（S-45）产出接管结论（可用/不可用 + 版本信息），是本模块全部功能的前提；
- **观测线**：容器观测（S-46）承载容器清单、日志与资源占用的只读呈现，是容器操作的对象来源与结果反馈视图；
- **操作线**：容器生命周期管理（C-12）承载六类容器状态迁移动作，受 BA 附录B 动作矩阵约束；
- **资源线**：镜像管理（S-47）、卷管理（S-48）、网络管理（S-49）承载三类 Docker 资源的治理，删除受 daemon 侧引用约束；
- **编排线**：Compose 项目治理（S-50）经 label 识别聚合项目并承载 up/down/restart/logs 项目级操作（ADR-013 CLI 编排）。

调用关系总脉络：daemon 探测与连接（S-45-01）为本模块全部读取与操作提供唯一通道判定；未装 Docker 安装引导（S-45-02）消费接管结论作降级呈现；容器列表与状态查看（S-46-01）为 C-12 全部动作提供对象来源（动作可用性按 BA 附录B 矩阵随当前态约束）；镜像/卷/网络删除（S-47-03/S-48-02/S-49-02）的可达性以容器引用解除（C-12-03 容器删除）为前提之一、以 daemon 拒绝为最终权威判定；Compose 项目自动识别（S-50-01）扫描容器 label 聚合项目清单，项目生命周期操作（S-50-02）与项目日志查看（S-50-03）消费识别结论定位工作目录（定位失败时兜底经 C-12 容器级操作达成）；全部变更类操作经 account-auth 审计契约留痕（R-03）；全部接口位于登录会话之后并受只读边界管控（account-auth S-03，全局中间件层面生效，不在本模块内单列调用）。跨模块契约与模块边界见附录B。

全部 L3 的 L4 组织模式判定（d1 分册 Step 1 自动判定）：均为 **standard 模式**——各 L4 相互独立、无「开始→结束」时序引导流程（Compose up/down/restart/logs 为并列的项目动作而非时序步骤），L4 一一映射为功能子模块。

### 应用域分层

> 按 DDD 战略设计，将应用域归入不同分层，决定后续详细设计的建模深度和投入策略。AA 应用域严格按照 DDD 四层划分，每个 BA L3 按 L3→DDD 四层归类原则归入对应分层。

| 分层 | 说明 | 包含功能模块 |
|------|------|-------------|
| 核心业务域 | 承载核心业务价值，有状态机和聚合根，深度建模 | 容器生命周期管理（C-12）——容器三态状态机（ADR-025）+ 动作矩阵为面板可操作主链 |
| 支撑业务域 | 为核心业务提供必要的业务支撑能力，包含业务规则，独立上下文 | Docker daemon 接管（S-45）、容器观测（S-46）、镜像管理（S-47）、卷管理（S-48）、网络管理（S-49）、Compose 项目治理（S-50） |
| 基础数据域 | 系统级引用数据，无业务状态机，薄适配 | —（本模块无：镜像/卷/网络为 daemon 实况投影，非面板维护的系统级引用数据） |
| 平台支撑域 | 纯技术能力，零业务语义，可复用 | —（本模块无：dockerx 适配器为技术实现资产，业务规则承载于各功能模块） |

### 2.1 核心业务域

**应用域概述**：承载容器状态迁移的操作主链：以 ADR-025 三核心态状态机与 BA 附录B 动作矩阵为业务规则核心，提供启动/停止/重启/暂停/恢复/删除六类动作，操作即时生效并记审计。服务的用户群体：管理员（admin）执行全部生命周期操作；只读用户（readonly）不触达本域任何操作入口（动作可用性矩阵由服务端同样校验，防越权直调）。

#### 2.1.1 容器生命周期管理（C-12）

**功能说明**：容器状态迁移的六类动作业务：启停/重启、暂停/恢复、删除；动作可用性受「面板态 × 动作」矩阵约束（BA 附录B.2），动作与当前态不匹配时服务端明确报错；删除仅对 stopped 态开放（MVP 无强制删除）；全部操作经接管通道即时生效，变更记审计（R-03）。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

##### 2.1.1.1 容器启停与重启（C-12-01）

**功能说明**：容器的启动（start，面向 stopped 态）、停止（stop，面向 running/paused 态，对 paused 等效先恢复后停止）与重启（restart，面向 running/paused 态）动作；入口按矩阵随当前态开放/禁用并提示原因。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| daemon 探测与连接（S-45-01） | 操作经接管通道下达到 daemon |
| 容器列表与状态查看（S-46-01） | 以容器清单为操作对象来源；操作后经列表刷新确认状态迁移结果 |
| 审计记录（account-auth S-04） | 启动/停止/重启为变更类操作，写审计（R-03） |

##### 2.1.1.2 容器暂停与恢复（C-12-02）

**功能说明**：容器的暂停（pause，面向 running 态——进程冻结、容器与资源保留）与恢复（unpause，面向 paused 态）动作；为 ADR-025 拍板动作集组成部分（排障冻结现场场景）。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| daemon 探测与连接（S-45-01） | 操作经接管通道下达到 daemon |
| 容器列表与状态查看（S-46-01） | 以容器清单为操作对象来源；操作后经列表刷新确认状态迁移结果 |
| 审计记录（account-auth S-04） | 暂停/恢复为变更类操作，写审计（R-03） |

##### 2.1.1.3 容器删除（C-12-03）

**功能说明**：删除前经确认（确认文案含容器名与镜像信息）；删除入口仅对 stopped 态容器开放，running/paused/过渡态禁用并提示先停止（MVP 无强制删除语义）；删除解除该容器对镜像/卷/网络的引用（资源线删除可达性的前提之一）。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| daemon 探测与连接（S-45-01） | 删除经接管通道下达到 daemon |
| 容器列表与状态查看（S-46-01） | 以容器清单为操作对象来源；删除后从清单消失 |
| 镜像删除（S-47-03） | 容器删除解除镜像引用，是镜像可删除的前提之一 |

| 审计记录（account-auth S-04） | 删除为变更类操作，写审计（R-03） |

##### 2.1.1.4 容器创建（C-12-04，v1.1 新增）

**功能说明**：经面板表单创建并启动容器（docker run 语义一步到位，BA ⚠️A18/D0 Q1+Q2）：镜像（本地不存在时自动先拉取——复用 S-47-02 拉取通道，拉取失败如实报错不创建）、容器名（白名单格式校验 R-14）、端口映射（多组宿主:容器）、环境变量（多组键值）、挂载（卷名或主机路径:容器路径，多组）、重启策略四选一（no/always/unless-stopped/on-failure）、网络选择（既有网络下拉，默认 bridge）。服务端逐项格式校验；创建后容器即时进入实况清单（零台账投影不变），动作矩阵按新容器 running 态天然覆盖。变更记审计（R-03，detail 含名称/镜像，不含环境变量值 ⚠️A9 同构）。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| daemon 探测与连接（S-45-01） | 创建经接管通道下达到 daemon（SDK ContainerCreate+Start，R-08 纪律由 dockerx 适配层承载） |
| 镜像拉取（S-47-02） | 镜像本地缺失时自动拉取（Q2 拍板：拉取失败如实报错不创建） |
| 网络列表查看（S-49-01） | 网络下拉数据源（默认 bridge） |
| 卷列表查看（S-48-01） | 挂载卷名下拉数据源 |
| 容器列表与状态查看（S-46-01） | 创建后实况清单刷新确认 |
| 审计记录（account-auth S-04） | 创建为变更类操作，写审计（R-03） |

### 2.2 支撑业务域

**应用域概述**：承载「接得上（daemon 接管）+ 看得清（容器观测）+ 清得掉（镜像/卷/网络治理）+ 编得了（Compose 项目治理）」的支撑能力：接入线产出唯一通道判定与降级呈现，观测线提供实况只读呈现，资源线提供三类 Docker 资源治理，编排线提供 label 聚合与 CLI 项目级操作。服务的用户群体：管理员（admin）执行镜像拉取/删除、卷/网络删除与 Compose 项目操作；只读用户（readonly）按 ADR-018 同等查看全部清单、日志与资源占用，无任何变更入口。

#### 2.2.1 Docker daemon 接管（S-45）

**功能说明**：对本机已有 Docker daemon 的探测、连接与降级呈现（R-12/R-15 只接管不重装）；产出接管结论（可用 + 版本信息 / 不可用），是本模块全部功能的前提。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（探测为系统机制；接管结论呈现两角色开放）

##### 2.2.1.1 daemon 探测与连接（S-45-01）

**功能说明**：探测本机 Docker daemon（`/var/run/docker.sock`）并建立连接、判定可用性，产出「可用（含 daemon 版本伴随信息）/ 不可用」结论；探测与连接为只读行为，进入容器业务时被动自动执行。系统内部机制，接管结论呈现于容器视图页头。

**涉及用户类型**：- [ ] 管理员（admin） - [ ] 只读用户（readonly）（系统内部机制，结论经页头呈现被两角色消费）

**调用关系**：

*（无调用，作为通道判定被本模块观测/操作/资源/编排各线消费）*

##### 2.2.1.2 未装 Docker 安装引导（S-45-02）

**功能说明**：未探测到可用 daemon 时的降级呈现：安装引导页说明本机未检测到可用的 Docker daemon、指引安装后再使用（不提供代为安装入口）；容器业务整体不可用，不得将「未安装」呈现为「无容器」空列表。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（两角色打开容器页均见引导提示，均无任何可操作内容）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|

#### 2.2.2 容器观测（S-46）
