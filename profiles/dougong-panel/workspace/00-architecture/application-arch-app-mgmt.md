## 第一部分：文档概述

### 1.1 背景与目标

将《斗拱面板 应用管理（app-mgmt）业务架构》（business-arch-app-mgmt.md v1.0）的 3 个 L3 关键业务按 DDD 四层归类为应用域，组织为功能模块/功能子模块，标注涉及用户类型与模块间调用关系，作为 PRD（D2）、API 设计（D3）与交互设计（D4）的功能组织依据。venv 创建与 pip 安装（R-08 参数数组）、systemd 服务单元与安全写入、nginx 反代建站为技术实现承载，其业务纪律（本机监听/端口冲突检测/单元安全写入/删除保守保全/审计脱敏/零遥测，⚠️A1~A12）落在本架构的模块说明与安全架构专节（附录C）中，实现归 D3 与后端工程。

DDD 归类结论（依据 d1 分册归类原则逐条判定）：

- **核心业务域**：应用部署与变更（承载应用档案聚合根候选与应用变更任务四态状态机 pending → running → succeeded/failed，是应用供给的单据型主链动作，互斥/审计/重试业务规则齐备）——满足原则一（状态机 + 聚合根候选 + 主链变更动作 + 产生任务记录）；与 env-mgmt C-14（env_install_task）、db-tools C-15（tool_deploy_task）同构判定；
- **支撑业务域**：应用清单与实况（含档案呈现/实况探测/依赖就绪度领域规则，被供给与运行两链消费）、应用运行与暴露（含服务操作互斥/参数安全写回/建站联动等业务规则，被日常运维消费）——两者含应用运维领域特有业务规则、被主链或运维消费，自身无独立状态机（服务运行态为 systemd 实况投影，端口监听为本机实况投影）；
- **基础数据域**：本模块无基础数据 L3——框架预设启动模板为编译期常量（非用户可配引用数据），不构成独立基础数据模块（与 db-tools 工具目录同判，随支撑模块承载）；
- **平台支撑域**：本模块无零业务语义的纯技术 L3——venv/pip/systemd/nginx 通道为实现细节（分别复用 env-mgmt 环境实况读契约、service-mgmt SysdGateway 同源适配层、site-mgmt 建站 OHS），业务规则承载于 C-16/S-60/S-61。

> 应用档案（app）为本模块聚合根候选（档案 + 服务落位引用 + 参数引用）；应用变更任务（app_task）为第二聚合根候选（四态状态机 + 同应用互斥 + 审计单据，与 env_install_task/tool_deploy_task 同构 4/4）；持久化口径（档案与任务台账落库）归 D2 领域建模落定；框架预设模板/服务单元路径/单元名前缀为编译期常量（非领域对象候选）。

> 模块编码衔接说明（编码规则的跨模块执行口径）：功能模块编码全局唯一，承接既有占用——account-auth C-01~C-03/S-01~S-05、panel-core S-06~S-12、monitoring S-13~S-16、service-mgmt C-04~C-05/S-17~S-18、file-manager C-06/S-19~S-25、site-mgmt C-07~C-10/S-26~S-30、database-mgmt S-31~S-37/S-55~S-57、terminal C-11/S-38~S-41、firewall S-42~S-44、docker-mgmt C-12/S-45~S-50、cron-backup C-13/S-51~S-52、env-mgmt C-14/S-53~S-54、db-tools C-15/S-58~S-59；本模块核心业务域模块编为 **C-16**（承接全局最大核心序号 C-15），支撑业务域模块自 **S-60** 起编至 **S-61**（承接全局最大支撑序号 S-59，依据「新模块在域内最大序号后递增」；已核验全仓 application-arch-*.md 无 C-16/S-60/S-61 占用）。

## 第二部分：应用架构

> 本章按应用域逐层描述功能模块与功能子模块。每个应用域有其概述，每个功能模块/子模块有功能说明及涉及用户类型。

### 本架构概览

应用架构按 DDD 四层聚为两个应用域：

- **核心业务域**承载应用供给状态链：应用部署与变更维持应用档案（聚合根候选）与应用变更任务（四态任务状态机 pending → running → succeeded/failed，同应用互斥，失败可重试），创建（目录校验 → venv → 依赖安装 → 服务单元生成）/依赖重装/删除三动作共用任务通道与审计纪律（端口冲突检测、删除保守保全、失败原因含 data.reason 如实可见）；
- **支撑业务域**承载「看得见 + 运行管得好」：应用清单与实况以档案台账叠加实时探测供给应用全景（供给与运行的共同数据底座），应用运行与暴露提供服务操作（启停/重启/自启，复用服务单元通道双入口并存）、参数编辑（.env 与启动参数安全写回）、日志查看（admin 专属）与站点暴露联动（消费 site-mgmt 建站反代）的运维能力。

调用关系总脉络：实况探测结果是创建/依赖重装/删除/服务操作的前置依据与按钮态数据源；变更任务完成后实况与档案刷新；供给产出（服务单元/venv/参数文件）是运行操作与参数编辑的对象；跨模块消费四模块——env-mgmt 环境实况读契约（Python 运行环境就绪度，本轮 +python 第九环境增量）、site-mgmt 建站能力（reverse_proxy 站点反代，站点暴露联动）、service-mgmt SysdGateway 同源适配层（服务单元操作，通用单元层仍归其治理）、account-auth 会话边界与审计（R-03）；软引导一条——file-manager 代码放置引导（无跨模块硬调用）；**跨模块被消费零条**（service-mgmt 服务列表可见应用单元为通用单元层如实呈现行为，非契约消费，⚠️A12）。全部变更类操作经 account-auth 审计契约留痕（R-03）；全部接口位于登录会话之后并受只读边界管控（ADR-018）。安全架构四道防线见附录C。

### 应用域分层

> 按 DDD 战略设计，将应用域归入不同分层，决定后续详细设计的建模深度和投入策略。AA 应用域严格按照 DDD 四层划分，每个 BA L3 按 L3→DDD 四层归类原则归入对应分层。

| 分层 | 说明 | 包含功能模块 |
|------|------|-------------|
| 核心业务域 | 承载核心业务价值，有状态机和聚合根，深度建模 | 应用部署与变更（C-16） |
| 支撑业务域 | 为核心业务提供必要的业务支撑能力，包含业务规则，独立上下文 | 应用清单与实况（S-60）、应用运行与暴露（S-61） |
| 基础数据域 | 系统级引用数据，无业务状态机，薄适配 | —（本模块无；框架预设启动模板为编译期常量随 C-16-01 承载） |
| 平台支撑域 | 纯技术能力，零业务语义，可复用 | —（本模块无；venv/pip/systemd/nginx 通道复用 env-mgmt/service-mgmt/site-mgmt 既有资产，业务规则承载于 C-16/S-60/S-61） |

### 2.1 核心业务域

**应用域概述**：承载应用供给的变更主链与任务状态机：创建/依赖重装/删除经异步任务执行（互斥、审计、失败可重试、输出如实），任务记录构成应用变更的可追溯台账；应用档案（聚合根候选）承载应用身份与落位引用。服务的用户群体：管理员（admin）执行全部变更；只读用户（readonly）仅可查看任务状态与输出（ADR-018）。

#### 2.1.1 应用部署与变更（C-16）

**功能说明**：应用供给主链：应用创建（前置校验 + venv + 依赖安装 + 服务单元生成）、依赖安装（重装/补装任务化）、应用删除（停服务撤单元撤档案，代码目录默认保留）、异步任务跟踪（四态状态机，输出尾部排障，失败原因含 data.reason，失败可重试）；安全纪律贯穿（参数数组 R-08、审计 R-03、单元安全写入、端口冲突检测、删除绝不静默删代码）。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（变更动作仅管理员，任务状态与输出两角色可看）

##### 2.1.1.1 应用创建（C-16-01）

**功能说明**：创建 Python 应用档案并落位运行环境（异步任务化，⚠️A1~A4）。**v1.1 起形态二选一（⚠️A13，D0 Q5）**：**①venv/systemd 形态（既有主线）**：前置校验（应用名唯一、代码目录存在、入口文件存在、Python 运行环境就绪——经环境实况读契约校验 python3/venv/pip，缺失如实拒绝并引导到环境管理；监听端口冲突检测——本机监听查询，占用如实拒绝）→ 在应用目录创建 venv（python3 -m venv）→ 依赖安装（存在 requirements.txt 则 pip 安装，无清单跳过）→ 生成 systemd 服务单元（框架预设 fastapi=venv 内 uvicorn 入口 + 模块:实例参数模板，或自定义启动命令〔venv 内相对路径白名单校验〕；默认绑 127.0.0.1；Restart=on-failure；单元文件经安全写入管线落盘，⚠️A6）→ 可选立即启动。**②容器化形态（v1.1 新增）**：前置校验（应用名唯一、镜像必填；无 Python 就绪度要求——运行时由容器镜像自含）→ 面板生成单应用 compose.yml（镜像/监听端口映射/环境变量/挂载/重启策略 + dougong-app 归属标签 ⚠️A13）→ 经 docker-mgmt Compose 项目创建通道落盘并自动 up -d（消费 docker-mgmt OHS，D3 定契约）→ 容器即时进入 docker-mgmt 实况清单（归属标签区分，全网视图照常可见）。两形态任务成功后档案生效；审计留痕（detail 不含参数值）。

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

**调用关系**：

**涉及用户类型**：- [✓] 管理员（admin） - [ ] 只读用户（readonly）

##### 2.1.1.4 应用变更任务跟踪（C-16-04）

**功能说明**：异步任务的观测与结果确认：任务状态（pending → running → succeeded/failed，⚠️A3）、目标应用与动作（创建/依赖重装/删除）、输出尾部（排障）、失败原因（依赖解析失败/网络失败/端口占用/环境缺失等如实分类，含 data.reason 具体原因，沿 env-mgmt/db-tools worker 错误形态先例）；同应用在途互斥（重复提交如实拒绝）；失败任务可重试（重试=重新执行依赖安装类步骤）；任务列表与单任务详情。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（ADR-018 全可看）

### 2.2 支撑业务域

**应用域概述**：承载「看得见 + 运行管得好」：应用清单与实况供给应用全景（档案台账 + 实时探测，供给与运行的共同数据底座），应用运行与暴露提供服务操作、参数编辑、日志查看与站点暴露联动的运维能力。服务的用户群体：管理员（admin）查看与执行全部运维；只读用户（readonly）查看清单/实况/任务（ADR-018），日志内容不可见（⚠️A8），无任何变更入口。

#### 2.2.1 应用清单与实况（S-60）

**功能说明**：应用档案台账（⚠️A1）与运行时实况（服务运行态/自启态/依赖就绪度/端口监听态）的合并呈现；纯读能力，是供给与运行两链的状态依据。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（ADR-018 全可看）

##### 2.2.1.1 应用清单呈现（S-60-01）

**功能说明**：应用全景列表：应用名、代码目录、入口文件、启动方式（框架预设/自定义）、监听端口、服务运行态、开机自启态、依赖就绪度（Python 环境/venv/依赖分层）、在途任务标记、关联站点提示（已建站 → 站点链接与前往站点管理引导；未建站 → 仅本机可达说明）；未创建应用呈现创建入口（admin）；应用管理页为本模块唯一页面载体。

**涉及用户类型**：- [✓] 管理员（admin） - [✓] 只读用户（readonly）（全部变更入口仅管理员可见，ADR-018 负空间）

**调用关系**：

| 调用模块/子模块 | 调用说明 |
|---------------|---------|
| 应用实况探测（S-60-02） | 列表条目的实况字段为探测结果投影 |

##### 2.2.1.2 应用实况探测（S-60-02）

**功能说明**：逐应用探测：服务运行态与自启态（经服务单元通道查询，⚠️A12）、venv 存在性与 Python 环境就绪度（消费 env-mgmt 环境实况读契约，⚠️A2）、依赖安装态（venv 内包环境查询）、端口监听态（本机监听查询）；纯读机制，被清单呈现/创建/依赖安装/删除/服务操作共同消费。
