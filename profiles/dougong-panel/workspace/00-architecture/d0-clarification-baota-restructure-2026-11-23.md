## 三、重组范围（D1-D4 待做）

目标信息架构（宝塔式「网站 / 容器」二分）：

- **网站管理**：收纳全部非容器化部署。现有 nginx 站点（静态 / PHP-FPM / 反向代理等）+ Python 项目（原 app-mgmt venv+systemd 形态）+ Node 项目（本轮新增托管能力，沿 Python venv+systemd 先例）。按项目类型分区呈现（宝塔「网站」菜单形态）。
- **容器管理**：收纳全部容器化部署。现有容器 / Compose / 镜像 / 卷 / 网络 + 新增「应用」分区（面板生成的单应用 compose）。
- **应用管理菜单**：删除独立菜单与路由；其能力按形态拆入上述两处。既有数据（`app` 表、迁移 015/017）不迁移不丢失，只改归属与入口。

需要的设计决策（D1 裁定并出 ADR）：Node 项目托管的进程管理方式与依赖安装通道；「应用」分区与 Compose 项目列表的数据同源关系；app-mgmt 容器化形态的修复（前端缺 image/env/mounts/restartPolicy 字段、`container_ops.go` 传 `"up -d"`/`"stop"`、`renderAppCompose` 丢挂载）随新落位一并处理；登录后监控总览资源条的「应用」计数入口同步（并行会话 bd25386 引入）。

## 四、范围边界（本轮不做）

- Compose yml 在线编辑器
- Java / Go 等其它运行时的项目托管
- app-mgmt 容器化形态的多容器 compose（单应用单 compose 单服务）
